## 1. 方向：从算子识别转为算子放置

### 1.1 决定

工作重心不再是**算子识别**（operator recognition），而是**算子放置**（operator placement）：
把用户显式给出的骨架算子分配到 CPU / GPU 等异构设备上运行。
编译器不再负责「从程序里猜出算子」，只负责把用户写下的算子落成 IR；
算子携带的 annotation 表达放置意图，放置决策本身成为工作的主体。

### 1.2 前端：只保留手动路径

- **半自动路径直接删除**，这是接下来要做的第一件事；不设过渡期，不保留可用开关。
- 删除范围：pass 及其注册、半自动路径的 CIR / 集成测试，
  以及仅为它服务的循环注解挂载——`CIRGenStmt.cpp` 的 `attachLoopAnnotations`，
  和 `emitForStmt` / `emitWhileStmt` / `emitDoStmt` 为传 attr 新增的形参（回到上游形态）。
- 工作流全部走手动路径：用户在源码里显式给出算子，算子上的 annotation 表达放置意图。
- 放置决策发生在**运行时**；编译期 annotation 是决策依据之一，
  编译器的职责是把这条信息完整、无损地传到 IR。

### 1.3 直接后果（初判）

- **语义变化**：annotation 从「算子种类 + 偏好」变为「算子 + 放置目标」；
  它的消费者从编译期 pass 变成运行时，编译期不再做「选设备」这件事。
- **论文重心**：主线从「识别的覆盖与恢复」变为「放置决策与设备适应」；
  识别相关的机制（store→alloca→load 溯源、输出形状按算子语义发明）退出叙事。
- **共用代码**：`CirCallLowering` 里为循环路径公开的 helper（`createToTensor` / `outputTensorType` /
  `createEmptyOutput`）随删除重新检查可见性，只剩一个使用者就收回内部。
- **历史文档**：[review/20260917.md](../review/20260917.md)、[report/20261012.md](../report/20261012.md)
  中关于半自动路径、识别算法的内容标记为作废；它们只保留作为背景。

### 1.4 决策记录（本轮拍板）

1. **放置决策在运行时**；编译期 annotation 是决策依据之一。
   影响：编译侧不新增「选设备」的 pass；`skeleton-preference-partition` 与 `skeleton-target-lower`
   现在承担的编译期选择语义**预计会被运行时取代**，不再留在编译期。
   原因：系统长期只在编译期做功、运行时没有任何投入，这两个 pass 就是这种分工的产物。
2. **annotation 设计取最简**：语法不限（编译器是我们自己的），但第一版要最简单、最不易出错，
   首要目标是把源码里的 annotation 信息完整传到 IR。表达力问题以后再说。
3. **算子集合需要扩展**，但清单不在此刻拍：等工业级 benchmark 定了，再按 benchmark 需要
   确定「基本算子 + skeleton 算子」各自支持哪些，可参考 cuBLAS / PyTorch 的算子库划分。
4. **半自动路径直接删代码**，不是从构建里摘除、也不是先禁用；删掉后构建产物自然就没有它了。
   （此前写的「先摘出构建」是错误表述，已作废。）

### 1.5 仍待定

- annotation 的具体语法与承载位置（下一个要设计的东西）；
- 运行时放置的形态：由谁读 annotation、在哪里做决策（独立 driver / 运行时库）还没讨论；
- 算子清单（等 benchmark）；
- 编译期现有两个 pass 在新分工下的去留。

## 2. GPU 支持：先要正确性

### 2.1 现状与问题

- GPU 路径靠手写搬运：`gpu.alloc` → 异步 `gpu.memcpy`（H→D）→ kernel → 异步 `gpu.memcpy`（D→H）→ `gpu.dealloc`；
  另有三条硬限制：只接受静态形状、只接受 identity layout、假设单输出。
- **已知缺陷（当前最高优先级）**：GPU 用例重复 100 次约 20 次输出垃圾（80 次正确）。
  自发现以来未修复。在修掉之前，GPU 上的任何放置实验都不可信。
- 待验证的怀疑：桥接里的异步拷贝与 kernel 启动、主机读取之间没有同步点
  （拷贝 token 没有被后续 kernel 或读取消费），`gpu.dealloc` 也可能与尚未完成的拷贝回写竞争；
  这类竞态正好表现为偶发脏数据。

### 2.2 方向

- 用 **UVM（统一 / 托管内存）** 取代手动 memcpy：主机与设备共享地址空间，
  kernel 直接读写主机分配的内存，删掉 alloc → memcpy → memcpy → dealloc 这条链。
- 先正确性、后性能：接受 UVM 的缺页迁移开销，先把 100/100 做出来再谈别的。

### 2.3 施工顺序（初判）

1. **复现**：把现有 GPU e2e 跑成 100 次循环，记录失败样本（期望 vs 实际），
   把「20%」变成可重复的失败率与可分析的样本。
2. **归因**：用最小实验区分「拷贝竞态」与「其他原因」（WSL2 / 驱动行为）。
3. **替换**：用 UVM 改写 GPU 桥接，先只覆盖现有静态形状用例。
4. **回归**：100 次全对，并把这个循环纳入日常回归。

### 2.4 待定

- UVM 的落点：host memref 直通（依赖 managed 分配），还是新增 managed alloc op；
- 是否保留 memcpy 桥接，作为不支持 UVM 的平台的回退；
- 20% 失败是否只在 WSL2 出现（需要裸机对照）。

## 3. 运行时

### 3.1 现状

- 系统目前**没有运行时**：放置决策没有承载者，target 在编译期就被选定了。
- 这是长期只在编译期做功、运行时零投入的结果。`skeleton-preference-partition` 与
  `skeleton-target-lower` 正是这种分工的产物，预计随运行时的建立被取代。

### 3.2 下一步

- 先想办法**注入一个最简单的运行时**，让放置决策有地方发生。
- 形态、注入点、与编译产物的衔接方式都还没讨论——这是接下来要细化的第一件事。

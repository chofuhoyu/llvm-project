# 组会汇报指南：Skeleton Dialect

## 主线

**Caelum论文的核心目标从「多目标代码生成」升级为「充分利用异构算力」：用 map/reduce 骨架算子组合程序员标记的纯函数，把程序的语义与偏好从源码传到 IR，再由一个独立的调度器把程序切分到不同异构算力上协同运行。**

---

## 第一部分：整体思想 —— 愿景的「变化」

### 1. 旧愿景 → 新愿景（核心对比）

| 维度 | 旧愿景 | 新愿景 |
|------|--------|--------|
| 核心目标 | 多目标代码生成 | 充分利用异构算力 |
| 层次 | 两层：语义表达 + 编译管线 | 三层：+ 调度层 |
| preference | 硬编码目标（程序员指定 CPU/GPU） | 软约束（调度器尊重、可调整/回退） |
| 谁决定去哪 | 程序员手动标注 | 调度器自动分配 |
| 形态 | 纯编译管线（MLIR pass） | 编译管线 + 独立用户态调度器 driver |

### 2. 变化的本质

- **目标变了**：旧愿景是"把一个算子送到正确的目标"（one-op-one-target），新愿景是"把整个程序切分成多块、同时跑在多个异构算力上，充分利用它们"——从"送对一个"变成"全用起来"。
- **论文范围变了**：语言、编译、调度是三个**并列**的层次。调度层的设想**早已有之**；这次的变化是把论文范围从**两层**（语言 + 编译）扩到**三层**（语言 + 编译 + 调度）——编译、调度的内容都没变，变的是"论文涵盖的范围"。
- **程序员角色变了**：旧愿景里程序员是"指定者"（硬编码 CPU/GPU）；新愿景里程序员是"建议者"（给出 preference 偏好），调度器是"决策者"（尊重偏好但可调整、可回退）。

### 3. 新愿景的三层结构

1. **语义表达层（语言）**：annotation 承载程序员意图 → 纯函数 + 骨架算子。
2. **编译管线层（编译）**：skeleton IR → linalg → 多目标 lower（已部分实现）。
3. **调度层（核心，规划中）**：程序切分 + 异构放置。

### 4. 调度层（核心，展开讲）

- **独立于 pipeline**：用户态独立调度器，与 clang 并列的 driver。
- **为什么可行**：纯函数的「无副作用」⇒ 切分是安全的；骨架算子的「可组合性」⇒ 程序可自然切分/重组为独立调度单元。
- **切分粒度**：动态可调、不固定——随异构设备加入/消失，动态求最优解。
- **调度时机**：静态切分 + 动态决策（编译期生成候选切分形态，运行时按实际设备状态选定）。
- **preference 是软约束**：调度器尽量"尊重"程序员意图；硬件不满足则改派其他设备，或回退 CPU。
- **异构范围**：当前聚焦 CPU + GPU（先把 GPU 搞定），未来扩展 NPU（待定）；跨机器是更远期工作。

### 5. 语义表达层简述（背景铺垫，不展开）

骨架算子（map/reduce）+ 纯函数（pure）+ region 嵌套 + preference；两条前端路径（手动 + 半自动）最终产出统一 IR。

## 第二部分：实现进展 —— 原型的「升级」

### 1. 一句话区别

**旧原型是「可行性验证」，新原型是「初步的通用框架」。**

### 2. 文字总结（主体）

**旧原型（custom_matmul，0711 前）—— 可行性验证**
- 只有一个 `custom_matmul` op，围绕"matmul → GPU"这一个例子。
- 目的是验证一条路走得通：程序员标注 preference，一路传到 IR、lower 到 GPU、跑出结果。
- 它的价值在于**证明了整条 pipeline 的可行性**。

**新原型（map/reduce，0711 后）—— 初步的通用框架**
- 把"一个 matmul"抽象成通用的 map/reduce 骨架算子，可组合、可嵌套。
- 5 个 pass 泛化（pattern-merge、partition 等），不再是给 matmul 定制的。
- 新增 CIR 前端（全手动路径 + 半自动路径），把 C++ annotation 接进来。
- 定位：为后续的调度层打基础——有了通用骨架，才能谈"切分 + 异构放置"。

### 3. 区别的本质

从"验证一个例子可行"到"建立一套通用抽象"：

- 旧原型回答"这条路走得通吗"，新原型回答"这套抽象长什么样"。
- 旧原型的产出是"一个能跑的例子"，新原型的产出是"一套可扩展的结构"。
- 这次升级的意义在于：调度层要做的"把程序切分到异构算力"，前提是程序已经被组织成**通用的、可组合的骨架**——这正是新原型在搭的东西。

### 4. 对比表

| 维度 | 旧原型（可行性验证） | 新原型（初步通用框架） |
|------|---------------------|----------------------|
| 目的 | 验证 preference → GPU 这条路可行 | 建立可扩展的骨架抽象 |
| op 集 | 单个 custom_matmul | 通用 map / reduce / vector_add / yield |
| pipeline | 为 matmul 定制 | 5 个 pass 泛化（含 pattern-merge） |
| 前端 | 无（纯手写 MLIR） | 新增 CIR 前端（手动 + 半自动） |
| 价值 | 证明链路可行 | 两个核心目标之一为调度层打基础 |

### 5. 0711 之后主要做了两件事

- **重构（7 月）**：把 matmul 单例抽象成通用 map/reduce 框架，MLIR 层端到端跑通。
- **工程化与质量（8 月）**：构建预设工程化、技术债清理、系统性 review 之前的源码。

### 6. 下一步

- 语言层与编译管线：完善半自动路径与全自动
- 调度层的实现做独立的用户态调度器 driver，首先聚焦 GPU

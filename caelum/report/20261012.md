# 【算子识别】

这份总结的主体是 Skeleton Dialect 的算子识别：怎么从 C/C++ 源码里把程序员标注的计算模式和纯函数认出来、变成 skeleton IR；围绕它做了调研、机制设计、原型系统开发与实验验证。中途项目方向做过调整，论文主贡献移到运行时调度，这部分一并记在最后。

## 一、调研

### 1. ClangIR 的 annotation 支持现状

目标是让程序员在 C++ 源码里用 `__attribute__((annotate(...)))` 标注计算模式，编译器认出来并在 IR 层切成可分配到不同设备的形态。调研了 llvm-project 仓库里已有的相关工作，检索关键词覆盖 `CIR annotation`、`cir.for annotation`、`CIR_LoopOpBase`、`attachLoopAnnotations`、`AttributedStmt annotate`。

- **PR #193329**（bcardosolopes，已合入）`[CIR] Add __attribute__((annotate(...))) support`：建立了 `cir::AnnotationAttr`、`cir.func` / `cir.global` 上的 `$annotations` 属性、CIRGen 层的 deferred annotation 机制、到 `@llvm.global.annotations` 的 lowering。范围限定在函数和全局变量，没有动 `CIRGenStmt.cpp`；`emitAnnotateAttr` / `getOrCreateAnnotationArgs` 当时是 CIRGenModule 的私有方法，注释写的是 "on a global"。
- **PR #207551** `[CIR] Preserve annotate attributes on record declarations`：仅 record 声明，当时 open。
- 循环级、语句级 annotation 的检索全部零结果。

结论：社区的基础设施（`cir::AnnotationAttr`）已经可用，我们在 `CIR_LoopOpBase` 上用这套现成的 attribute 做循环级 annotation，再通过自己的 pass 把信息传到 Skeleton 方言。这部分是社区还没覆盖的。

### 2. 为什么语句级 annotation 必须在结构化 IR 层做

分析了传统 Clang → LLVM IR 路径丢注解的两个层次的原因：

- **Clang 侧**：`CodeGenFunction::EmitAttributedStmt` 的 switch（`clang/lib/CodeGen/CGStmt.cpp`）只处理 `nomerge` / `noinline` / `alwaysinline` 等属性，`attr::Annotate` 落到 `default: break` 直接丢弃。原因是 `__attribute__((annotate))` 在 Clang 生态里的原始定位是标注声明（变量、函数、结构体成员），对应 `llvm.var.annotation` / `llvm.ptr.annotation` 两个 intrinsic，语义是给内存位置打标签，与循环这种控制流结构无关。
- **LLVM IR 侧**：循环不是 IR 实体，而是一组基本块靠分支指令连起来的拓扑结构（`LoopInfo` 是后验推断）。annotation 没有挂载点——挂在 header 的 phi 上、latch 的 branch 上都是循环的局部片段，语义不完整；循环展开、基本块合并等优化还会让位置失效。`!llvm.loop` metadata 是为循环优化参数专门设计的固定语义通道，不承载程序员的任意注解。

而在 CIR 里，`cir.for` 是一个 op，有自己的 location、region、attributes。结论是语句级 annotation 的信息传递不是「选择在 CIR 做」，而是「只能在结构化 op 上做」。

### 3. 异构 offload 模型的缺口

现有方案的回退判据：OpenACC 的 `if` 子句、OpenMP target 的 `if` 子句和 `OMP_TARGET_OFFLOAD` 环境变量，判断的都是设备**在不在**（存在性、实现是否支持），或者程序员手写的一个布尔表达式。「设备在、但被别的进程占满」这种情形不在覆盖范围内，程序只能在被占满的设备上排队。这是后来论文核心主张针对的模型缺口。

差异化定位调研了三条现有路径：重写型方案（CUDA / SYCL / Kokkos，要求重写、两份代码）、offload 标注（OpenACC / OpenMP target，单源增量但回退判据是设备存在性、决定权在程序员写死的条件）、显式任务运行时（StarPU 这类，要程序员手写任务图，含依赖分析、就绪队列、拓扑序）。缺口是「单源 + 增量 + 目标选择在运行时」三者同时满足的方案不存在。

### 4. 论文场合调研

目标定为 TPDS（IEEE Transactions on Parallel and Distributed Systems，A 类期刊，滚动投稿）。这个选择的直接后果是：审稿人是并行/分布式系统方向，不看 dialect 设计是否优雅，看的是跑起来怎么样、比什么快、在什么规模上成立；因此论文按系统论文写，主贡献定在运行时调度与设备适应，编译管线（含算子识别）作为让调度成为可能的手段。

## 二、算子识别的机制与算法设计

算子识别分成两条前端路径，最终产出同一份 skeleton IR。

### 1. 手动路径：识别对 skeleton 辅助函数的调用

程序员在头文件里 include `mlir/include/mlir/Dialect/Skeleton/SkeletonOps.h`（只声明、无实现的辅助函数），用 `skeleton_map` / `skeleton_reduce` 组合标了 `__attribute__((annotate("skeleton.pure")))` 的纯函数，宿主函数标 `skeleton.region`，偏好标在同一个注解的第二个参数上。pass `cir-call-to-skeleton` 把 `cir.call @skeleton_map` 重写成 `skeleton.map {pure_fn = @my_add}`。

识别链路上的几个算法点：

- **纯函数引用解析**。`pure_fn` 必须解析到 `func.func` symbol，给异构设备检测和 pattern merge 提供锚点。C++ 里把纯函数经局部变量传递（`auto fn = &my_add`）时，Clang 生成的是 `store` 到 alloca 再 `load`，最初的实现只认裸 `cir.get_global`，这类调用被拒。实现改为穿透 `cir.cast` 后跟随 load 链、正向走到支配该 load 的那一条 `cir.store`（对照 CIRSimplify 的 `findDominatingInitOp`），回到被存入的 global 地址；有歧义的写和非 alloca 的地址来源保守失败。
- **注解语义集中**。`skeleton.*` 注解的布局（哪个参数是算子名、哪个是偏好）原先在三个文件里各自猜、直接吃裸字符串，非法值要到下游 `PreferenceAttr` verifier 才被拒。改为 `CirSkeletonAnnotations` 单一持有：`SkeletonOpType` / `SkeletonPreference` 枚举、存在性查询、在带注解的 op 上校验参数取值的类型化读取器。非法算子和非法偏好在注解处就带定位地失败，不再静默默认。
- **参数来源解析**。map 的输入原先按 memref 参数位置匹配，调用实参顺序与宿主形参顺序不一致、或只传子集时会静默错位绑定。改为从 call 的操作数解析：`mapDataOperandToMemref` 先确认操作数是直接宿主参数，再按它的参数序号取对应 memref；不是直接宿主参数的（中间值）发警告并中止 lowering，不猜。
- **数组形状**。宿主参数原先用裸 `float*`，长度在程序里不存在，pass 只能按算子语义「发明」输出形状（map → 一维动态、reduce → rank-0）。改为把数据参数按引用传，让类型本身携带长度：数组引用 `float (&a)[4]` → `memref<4xf32>`（嵌套 `[2][4]` 贡献外层维度），项目自带的 `skeleton_detail::span<T>` → `memref<?xf32>`（元素类型取 `data` 的 pointee，长度取 `size` 成员）。`resolveDataOperands` 在模块还是 CIR 时校验所有数据操作数同元素类型同形状——`skeleton.map` 的 verifier 单独看会放过「静态维对动态维」这种组合。两个运行时长度只有到运行时才能比较，所以改写后的宿主里带一段 `arith.cmpi` + `cf.assert` 检查。这条同时解开了 GPU 路径：静态形状的宿主（数组引用）现在能过 GPU 桥接。

### 2. 半自动路径：识别带注解的循环

程序员直接标注 for 循环：

```cpp
__attribute__((annotate("skeleton.region", "CPU")))
for (int i = 0; i < N; ++i)
    C[i] = A[i] + B[i];
```

`cir-loop-to-skeleton` 把整个循环识别成 `skeleton.map`。与手动路径的区别是**算子类型由循环形状推断，不由注解点名**——注解只说「这一段交给 skeleton 编译器」。

识别算法（`CirLoopToSkeleton.cpp`，677 行）：

- 匹配一个 canonical 的升序单位步长 `cir.for`：归纳变量从 0 起、条件区是 `i < bound`、步进区是 `++i`，循环体是直线标量代码。
- **参数溯源**：反向追 `store → alloca → load`，把循环体里读写的指针还原成宿主入口块参数，区分输入数组与输出数组。
- 循环形状（`MapPattern` 结构）匹配 cond 与 step 两个 region；输出形状因为循环次数是运行时值，与手动路径的 span 宿主一样是动态的，因此也带同一段运行时一致性检查。
- 循环体的标量计算抽成一个 `func.func` 纯函数（走与手动路径同一个 `CirFuncToArith` 翻译），宿主 `cir.func` 重写成「每个输入数组一个 `memref<?xelt>` 参数、返回输出 `tensor<?xelt>`」的 `func.func`，最后发出引用该纯函数的 `skeleton.map`。
- **循环上界必须是宿主参数**：改写时迭代次数取自输入张量的 extent，所以 `for (i = 0; i < N - 1; ++i)` 这类会被静默当成遍历全部元素。现在要求上界能解析到宿主参数，拒绝常量与计算出来的界。这是必要条件而非充分条件——CIR 里没有「循环上界 ↔ 数组长度」的联系，`f(3, A, ...)` 传一个长度对不上的参数仍然会被改写成覆盖全部，这一条是显式的假设。
- 支持集合刻意收窄：while / do-while、累加型（reduce）循环、任何非 canonical 形状都报出来并原样保留。

这条路径的支持范围与手动路径共用同一套机制而不是复制一份：`createFuncFromCirBody` 移到 `CirFuncToArith` 供两条路共用，`createToTensor` / `outputTensorType` / `createEmptyOutput` 公开出来让循环路径拼出同样的宿主函数体。

### 3. 支撑识别结果的降级链设计

识别出的算子往下走一条固定的链路，这一轮把其中的判定做得更严、语义向 linalg 看齐：

- `skeleton-pattern-merge`：`map{pure_fn=@add}` 合并成命名 op。判定从「精确 op 计数 + 操作数顺序」改成根 op 匹配（根 op 是 `arith.addf` / `arith.addi`，接受交换律，容忍无关指令），并补上 rank 与元素类型检查——原先 2D 的 `map{pure_fn=@add}` 会被合并成只允许 1D 的 `vector.add`，产出一个过不了 verifier 的 IR。
- 命名 op 定名 `skeleton.vector.add`（点号，向 `linalg.add` 看齐），并且**类型多态**：一个 op 承载浮点与整数加法，不引入 `vector_addi`。依据是 verifier 本来只查 rank 和元素类型一致、下游 `linalg.add` 本身多态，「只能浮点」只是 pattern-merge 判定层的实现选择。
- `skeleton-to-linalg`：map → `linalg.generic`、reduce → `linalg.reduce`、vector.add → `linalg.add`，preference 以 discardable 属性保留。纯函数的函数体在这里被 clone 进 region（`IRMapping` 映射参数 → block args，去掉 terminator，`func.return` 换成 `linalg.yield`），不是一次函数调用。
- `skeleton-preference-partition` 按 preference 把 linalg op outline 进独立 `func.func` 并标 `skeleton.target`，`skeleton-target-lower` 按它生成 CPU（`scf.for`）或 GPU（`scf.parallel` + 设备内存桥接）代码。

这一轮还拍板/落定了几项语义：`map` / `reduce` 的 `pure_fn` 与 region body **二选一**（原先只拦「两个都没有」，hybrid 形态能过验证但没有任何消费方，属无语义死 IR）；结果类型从 `init` 推导（向 linalg 的 DPS 一致）；destination 参数改名 `output` → `init`；手动路径用**返回值风格**（辅助函数返回新张量，不传目标缓冲区），依据是 tensor 层的 `outs` 是 SSA 值语义、提供初值与形状、返回的是拷贝，原地写只发生在 bufferize 之后的 memref 层。

### 4. 评估算子的基准与实验设计（尚未执行）

- **负载**：4–6 个代表性 kernel，至少含一个 reduction、一个 stencil、一个稠密线性代数，覆盖 PolyBench / Rodinia 里几个有代表性的即可。这决定了要走通哪些骨架算子。
- **基线**：OpenMP（CPU 地板）、OpenACC 或 OpenMP target（GPU offload，主要对手）、手写 CUDA（只用来证明性能在可接受范围内，不追求打赢——MLIR 原型在绝对性能上赢不了手写 CUDA 是结构性的）。
- **指标**：相对基线的性能比、设备被占满时的退化与回退表现、annotation 的编译期开销、随规模的扩展曲线。
- **消融**：preference 软 vs 硬、单候选 vs 多候选——分别对应论文的两条主张。
- **核心实验（设备争用曲线）**：横轴是 GPU 争用程度（0% / 25% / 50% / 75% / 100%），纵轴是同一负载的完成时间，三条曲线分别是我们的系统（GPU 空闲上 GPU、被占回退 CPU，基本平）、OpenACC / OpenMP target 版本（回退只看设备存在性，被占满时不触发，时间飙升）、纯 CPU OpenMP 版本（作地板）。这条曲线现在还不存在，是后续第一步要做的。

## 三、原型系统开发

这一阶段相对 `caelum/main` 共改动 91 个文件、+7467 / −26 行。

### 1. IR 层（`mlir/{include,lib}/mlir/Dialect/Skeleton/IR/`）

四个 op（`map` / `reduce` / `vector.add` / `yield`）加 `preference` 属性。这一轮补强了 verifier：MapOp 查输入 rank 等于 init/result、静态维对得上；ReduceOp 查 rank-0 输入会被拒；`PreferenceAttr` 的非法取值补了反例测试。属性体系上，`skeleton.target` 从裸 `StringAttr` 改成强类型的 `#skeleton.target<"GPU">`（有 verifier 限 CPU/GPU、有 mnemonics），三个消费点的字符串比较一并改掉，并在 target-lower 之后清除，避免这个方言属性泄漏到不加载 skeleton 方言的下游（如集成测试里的 mlir-runner）。

### 2. Transforms 层（5 个 pass）

- `skeleton-preference-partition`：修了链式 producer-consumer 的正确性缺陷——Phase 1 把输入快照成 `Value`，Phase 2 处理 producer 时 `replaceAllUsesWith` 会让 consumer 的快照悬空，写出引用函数外部值的非法 IR。改为从活着的 op 重建 operands。
- `skeleton-target-lower` 的 GPU 桥接（`gpu.alloc` → `gpu.memcpy` H→D → call → `gpu.memcpy` D→H → `gpu.dealloc`）：bufferize 函数边界改用 identity layout，让 host 操作数静态连续（`gpu.memcpy` 是裸字节拷贝）；设备 alloc 类型改为从 host memref 类型推导，不再从 shape + 元素类型重建；动态形状的 host memref 从「发 warning 后跳过桥接、把 host memref 直通 kernel」改成显式报错并让 pass 失败。
- `skeleton-to-linalg`：拒绝多 block / 未定义的 `pure_fn`（原先只 clone `front()`，带 if/else 的纯函数体会被静默截断——不报错、结果不对，是最危险的一类失败）。

### 3. 前端（`clang/lib/CIR/Dialect/Transforms/`）

上一轮变更审查时，手动路径实际是空转：pass 读的是名为 `skeleton.op` / `skeleton.pure` 的**直接属性**，而 C++ 的 `annotate("skeleton_op", ...)` 经 CIR codegen 落到 op 上的是 `annotations` 数组里的 `cir.annotation`，全项目没有任何地方生产前者，所以 `opDecls` 恒空、pass 在一开始就 return。这一轮把两条路径都做实了：

- **手动路径打通到能跑**：注解解析、纯函数 `cir.func` → `func.func`、`cirTypeToStdType` 这类手写类型转换换成正规的 `CirScalarTypeConverter`（`mlir::TypeConverter`，修了 `cir::IntType` 匹配不上导致整数 map 被拒的缺口）、纯函数体翻译成 arith（`CirFuncToArith`，处理 Clang codegen 的 alloca/store/load 形式，支持常量与整数/浮点的 add/sub/mul/div/rem、`cir.fmuladd` 展开、fneg 与整数取负，其余控制流、cmp/select/cast、调用、逃逸 alloca、volatile/atomic 一律带诊断拒绝而不是静默丢）、pass 拆成 `CirCallAnalysis.cpp` + `CirCallLowering.cpp` 两个文件。
- **半自动路径从 stub（只发 warning）到实现**：`CirLoopToSkeleton.cpp` 677 行。
- **新增模块**：`CirSkeletonAnnotations`（注解语义单一持有）、`CirCallAnalysis` / `CirCallLowering` / `CirFuncToArith` / `CirScalarTypeConverter` 四个头文件与实现。
- **用户侧入口**：`mlir/include/mlir/Dialect/Skeleton/SkeletonOps.h`，`skeleton_map` 是 variadic template（与 `skeleton.map` 的 variadic `ins` 对齐），并且 `cir-call-to-skeleton` 会删掉 clang 留在 module 上的 `cir.*` / `dlti.*` 属性（下游 mlir-opt 不注册 CIR 方言，留着就解析不了）。

### 4. 测试

- **单元测试 9 个**（`mlir/test/Dialect/Skeleton/`）：op 正/反例、pattern-merge、to-linalg、preference-partition、target-lower 正/反例、finalize-memref-to-gpu、target 属性反例。
- **集成测试 12 个**（`mlir/test/Integration/Dialect/Skeleton/`）：CPU 侧有纯 MLIR 的 vector.add / map / reduce / matmul，以及 C++ 到运行的端到端；GPU 侧是 matmul 与 C++ 到 GPU 的 e2e。
- **CIR 侧测试**：`skeleton-manual-path.cpp`（手动路径的 C++ FileCheck）、`skeleton-loop-path.cpp`（半自动路径的 C++ FileCheck）、`cir-call-to-skeleton.cir` 及其非法算子、非法 region、非 skeleton 残留、span 形状四个附加用例、`cir-func-to-arith.cir`、`annotate-loop.cpp`。集成测试去掉了文件名上的 `test-` 前缀。
- **e2e 的剥壳脚本** `skeleton-peel-module.sh`：原先用内联 awk 假设「第一行是 module 头、最后一行是 `}`」去剥 cir-opt 打印的 module 外壳再与驱动拼接，格式一变就会静默拼出坏 MLIR。改成校验外壳形状、不匹配就大声失败。

### 5. 工程化与文档

- **构建**：`.profile/` 独立仓库托管个性化配置，`bootstrap.sh` 幂等生成软链与实体 `CMakeUserPresets.json`（从模板注入 `SKELETON_ROOT`）；带 CUDA 与不带 CUDA 的对应预设共用同一 binaryDir，编辑体验一致；`CLANG_ENABLE_CIR` 补进预设，`cir-opt` 可用，CIR 测试才跑得起来。ccache 由 `SKELETON_ROOT` 锚定，主 checkout 与所有 worktree 共享。
- **文档**：`caelum/` 下形成三类产出——组会报告（`report/`）、代码带读与变更审查（`review/`）、设计决策（`doc/`）。做过一次全分支变更审查（报告 + 复审），写过五站的代码带读向导与按执行顺序排的 TODO 清单（①–⑰），另有两份针对具体提交的带读。

## 四、实验与验证

### 1. 当前测试结果（本机重跑）

- Skeleton 单元测试 **9/9 通过**。
- Skeleton 集成测试 **12/12 通过**，其中包含 GPU 的 `skeleton-matmul-gpu.mlir` 与 C++ → GPU 的 `cpp-map-add-static-gpu.mlir`（本机 RTX 5060 Ti，WSL2，CUDA 在 `/opt/cuda`）。
- CIR 侧测试：`build/tools/clang/test/CIR/Transforms/` 共 109 个用例，108 通过；唯一失败的 `abi-lowering/x86_64-struct-padded.cir` 是 ABI lowering 的用例，与 skeleton 无关（上游合并带来的既有失败）。skeleton 相关的 CIR 用例（`cir-call-to-skeleton*`、`cir-func-to-arith`、`cir-loop-to-skeleton`、`skeleton-manual-path.cpp`、`skeleton-loop-path.cpp`）全部通过。
- 上一轮审查时的基线数字是 7/7 单元 + 5/5 CPU 集成 + 1/1 GPU 集成，全部通过；那一轮同时确认了 MLIR 层（IR + 5 个 pass + CPU/GPU lowering）端到端数值正确。

### 2. 端到端实验（C++ 源码到可执行结果）

- **手动路径**：`cpp-map-add.mlir`（`clang -fclangir` → `cir-opt -cir-call-to-skeleton` → `mlir-opt` 全链 → `mlir-runner`），输入动态形状 `memref<?xf32>`，输出 `C = A + B = [6, 8, 10, 12]`；`cpp-reduce-sum.mlir` 是 reduce 版本。
- **手动路径静态形状**：`cpp-map-add-static.mlir`，宿主参数是数组引用，改写后是 `memref<4xf32>`。
- **半自动路径**：`loop-map-add.mlir`，源码是一个带注解的 for 循环、不含任何 skeleton 头文件或辅助函数调用，`cir-opt -cir-loop-to-skeleton` 把它变成纯函数 + 带 `skeleton.map` 的宿主，数值同样是 `[6, 8, 10, 12]`。
- **第一条从 C++ 编到 GPU 的端到端**：`cpp-map-add-static-gpu.mlir`，源码与 CPU 版只差注解里的 preference；因为数组引用给出了编译期 extent，改写后是 `memref<4xf32>`，能满足设备桥接对操作数的要求（动态形状会被桥接拒绝）。执行驱动仍是 CPU 版那个手写 MLIR `@main`——两侧宿主签名相同，只是 lowering 尾巴不同。
- **反例验证**：非法算子注解、非法 preference 注解、非 skeleton 函数残留（模块末尾硬报错）、span 宿主的形状校验、`cpp-map-add-mismatch`（两个运行时长度不一致必须在运行时被 `cf.assert` 拦住）、循环上界非参数（`N - 1`）必须被报告并原样保留。

### 3. 还没做的实验

设备争用曲线（论文核心图）还没有。它需要先写出调度器驱动器（`mlir/tools/skeleton-driver/`，与 clang driver 同级的独立程序，拥有编译管线：输入是 skeleton 层 module，查设备状态、按设备状态与 preference 给候选排序、用选中的 target 跑完剩余管线并执行、走不通就换一个 target 重来），并给 `skeleton-preference-partition` 加一个 `-skeleton-force-target=CPU|GPU` 选项（几十行）。另外要先摸清两台机器的 GPU 型号，以及能不能可控地制造「设备不可用」与「设备被占满」两种状态。

## 五、方向调整（论文定位）

做半自动路径时暴露的问题直接改变了技术路线：ClangIR 相比 C++ AST 已经丢掉了大量信息，一个算子要几百行模式匹配，而且其中一半是在猜——反向追 `store → alloca → load` 才能找到宿主的入口参数、输出形状按算子语义凭空发明、长度在程序里根本不存在。算子种类一多，这套恢复规则的组合会迅速失控。

调整后的路线：**在 codegen 阶段同时产出两种方言**。标了 skeleton 的部分直接生成 skeleton dialect，其余部分照常生成 ClangIR，两者在同一个 MLIR module 里共存，之后走 MLIR 自己的 lowering 管线。ClangIR 的地位从「基础」变成「把 C++ 程序完整带进 MLIR 世界的工具」。理由是可陈述的设计约束：提升所需的语义信息（容器类型、元素种类、形状来源、生命周期）在源码层是完整的，一旦降低到任何中间表示就只能靠模式匹配重建，重建规则会随算子种类增长而迅速复杂化。

论文定位随之改为系统论文，主贡献是运行时调度与设备适应（项目三层规划里一直标着「规划中」、独立于 pipeline 的调度层），编译管线（含算子识别）是让调度成为可能的手段。核心主张针对模型层面的缺口：现有异构编程模型能表达「设备在不在」，表达不了「设备忙不忙」；回退与否由程序员写死的条件决定，不是由运行时按实测状态决定。做法是让程序员只表达计算模式与偏好（软约束），编译期生成候选切分形态，运行时按实测的设备状态（含争用程度）选定并回退，同一份二进制在设备可用性变化下保持可执行且性能不崩。

调度器的形态与功能边界也定下来了：

- **形态**：与 clang driver 同级的独立 driver。判据是它有没有拥有管线——输入是 skeleton 层的 module，自己查设备状态、决定 target、跑完剩下的管线、失败换一个 target 重来。
- **功能**：砍到四件事（查设备状态 → 按设备状态和 preference 给候选排序 → 用选中的 target 跑完管线并执行 → 走不通换另一个 target），不做完整的策略框架，也不做分布式。
- **preference 的地位**：从源里的硬标注降级成驱动器排序时的权重之一——这是整条主张的实现落点。
- **与图调度的区别**：纯函数无副作用、骨架算子之间只有 region 嵌套带来的结构层次、没有任意依赖图，要解决的是设备选择与适应，不是 StarPU 那类任务图调度，难度差一个数量级。

## 六、按顺序排的后续台阶

- **台阶 0（台阶 1 跑在真实 C++ 上的前提）**：
  - 宿主 API 携带长度而不是裸指针——已落地（编译期长度用数组引用、运行时长度用自带的 span）；剩下的缺口是「span 的值进 IR」：现在长度是以 memref 描述符的动态维形式到达 skeleton op 的，要让它来自源码里的 `span.size` 得先做前提 3。
  - 运行时长度下 GPU 桥接要支持动态形状——只绕开了一半，静态那半（数组引用）已经能跑，span 那半仍被拒。
  - 宿主周围能有普通 C++ 代码——现在两条路径都在 module 末尾对残留的 `cir.func` 硬报错，所以 `main`、调用宿主的人、任何非 skeleton 函数都编不过；方向是宿主改成函数级、保留符号，签名/长度/返回在 host–skeleton 边界上定。
- **台阶 1**：驱动器 + 整模块的 target 选择，做出设备争用实验。输入先用纯 MLIR（现有静态形状 matmul 测试就够），把不确定性最高的部分先验证掉——设备状态怎么查、「被占满」怎么判定、回退怎么触发、候选怎么排序，这些和输入是不是 C++ 完全无关。
- **台阶 2**：preference 软化，每个 op 出 CPU / GPU 两个候选，preference 是权重之一而不是二选一；顺带把「重复 outline 去重」一起考虑（相同 preference、相同 op 形态、相同操作数的 op 现在会各自 outline 成独立函数，而调度器很可能整个接管这件事）。
- **台阶 3**：候选共存的语义边界与数据迁移。同一份计算的两个版本要共存于同一 module，GPU 设备内存桥接与 CPU 路径必须同时成立。到这一步，设备 memref 用 host memref 类型（靠 NVPTX generic 恰好覆盖 global 才跑得通）的地址空间问题会真正爆掉，单输出假设（硬编码 `call.getResult(0)`）也要一并处理；紧接着是数据在 CPU/GPU 边界上的搬运，长度在这里真正被需要。
- **台阶 4**：动态粒度调整，一个算子可以切开分到多个设备上，切多细由运行时的设备数量和负载决定。
- **节奏**：台阶 0 + 台阶 1 打通驱动器和设备争用实验；台阶 2 + 台阶 3 每 op 出双候选再解决候选共存；台阶 4 + 评测；成稿投出。收敛线定在 2027 年 3 月左右。

**暂缓不做**（判断标准只有一条：是不是设备争用曲线那条曲线的必要条件）：行级嵌套（`map` body 内嵌 `reduce`）、多 block 纯函数体的 clone、lambda 作为 `pure_fn`、`dlti` 的外科化删除、`Step`/`Phase` 注释命名统一、给 upstream 提 `linalg.map` 文档 arity 错误的 issue、memref 类型系统的认知整理文档。

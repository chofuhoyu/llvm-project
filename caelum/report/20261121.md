## 一、起点：决策点已经移到运行时

上一阶段结束时，最小运行时已经成立：编译期只切分算子单元、记录偏好，宿主不再绑定设备；
运行时在每次调用时做出放置决策，缓存中没有可用实现时回到编译期，按该单元的中间表示即时
生成目标代码。由此得到两条路径：产物只含 CPU 实现与可重编译的中间表示；经入口执行时，
GPU 代码在运行期产生。同一进程内，同一算子可以在不同设备间重新决策。

这证明了一件事：算子放置的决策点可以从编译期移到运行时。但它没有回答下一层问题——决策点
移走之后，编译器、前端、入口和验收各自应该长成什么样。这一阶段的工作就是回答这个问题。

## 二、审查：从“能跑”到“能证明”

以最小运行时为起点，我把整条链路的代码、测试和文档读了一遍。审查最重要的结论不是又找到
几个缺陷，而是发现原来的验收标准太弱：链路能跑，但“绿了”证明不了它声称的事情。

两个例子。其一，C++ 的 GPU 用例只比对数值；设备代码编译失败时，运行时会静默回退到 CPU，
程序照样输出正确结果。于是“数值正确”无法区分“真的在设备上跑”和“悄悄退回 CPU”。其二，
设备同步调用返回成功，但返回值只说明“某个上下文同步成功”，不说明等到了 kernel 所在的
上下文；这两件事在代码里没有被区分开。

这类问题不是功能缺失，而是证据缺失。审查之后，验收标准从“功能存在、测试通过”收紧为
“证据能够支撑具体的断言”：放置要有可检查的记录，性能要在数值正确之后才计时，文档要与
代码一致。这个标准的改变，决定了后面大部分工作的方向。

## 三、并到 cpp-codegen-operators：C++ 成为程序语言

这一阶段先把最小运行时之后的工作并到 `caelum/cpp-codegen-operators`。主线是把 C++ 从
“算子描述语言”变成“程序语言”。此前 C++ 主要用来写算子片段，`main`、控制流和标准库调用
都要手写 MLIR；合并之后，整段程序经 ClangIR 进入 MLIR，算子只是其中被切走的一部分。

与之一同改变的是边界。原来按整模块替换，现在按函数切分：宿主保留符号和 C++ 签名，算子成为
独立单元，结果写到目的地参数；形状来自参数类型，而不是从算子语义反推。半自动路径被删除，
不再从带注解的循环里反推算子——这是一次有意的收窄：放弃“从已经降低的形态里猜意图”，
只保留“用户显式写出算子、annotation 只表达算子与放置偏好”。

`preference` 的地位也随之改变：它是运行期决策的依据之一，不再是编译期绑定的目标。至此，
编译器的职责收敛为两件事：把用户写下的算子落成 IR，把源码里的 annotation 完整地带下去。

## 四、skeleton++ 与 mlir-skeleton-driver：把两条路径收成一个入口

`skeleton++` 与 `mlir-skeleton-driver` 在这一阶段从引入到收口，成为编译期与运行期之间的
统一入口。

`mlir-skeleton-driver` 是运行期的入口。它接收前端产出的模块——宿主与算子单元还在同一个
模块里——或者一个已经发射的产物；自己把单元切成逐算子的模块，把每个算子调用改写成
“解析 + 间接调用”，JIT 执行宿主。每次解析按单元声明的偏好和设备探测结果选设备，设备不可用
或放不下时回退 CPU；缓存未命中时回调 driver，把这个单元的骨架 IR 编成目标代码。`--emit`
则链接一个只含 CPU 实现、内嵌 IR 的独立可执行文件。

`skeleton++` 把前端和入口串起来：`clang++` → `cir-opt` → driver，一条命令完成构建或 JIT。
两者合起来，前端只负责产出模块，入口在同一进程里完成切分、JIT 与按需重编译；“编译期产物”
和“运行期决策”因此落在同一条命令里，而不是两套互不相干的工具。产物的形态也由此确定：
CPU 实现 + 可重编译的 IR；GPU 代码的唯一来源是运行期重编译。同一份产物可以单独按 CPU
运行，也可以被 driver 读回、补出 GPU 实现后再运行。

为了让“能证明”落地，这一阶段还用 benchmark 确定了第一批算子（softmax、layernorm、matmul、
逐元素 add），并把计时放在数值校验之后；GPU 用例开始断言实际放置，而不只是比对结果。
远端 GPU 主机上的三组测试通过。需要说明的是，现有耗时是 debug 构建下的一次性记录，只用于
看趋势，不作为性能结论。

## 五、问题：一直在往下做，没有先定义“做到哪里算完”

把这段工作连起来看，问题很清楚：我一直在往下做。运行时缺证据，就补 trace 和断言；断言的
前提不成立，就继续追到 ABI、上下文和测试；文档和代码对不上，就再收一遍文档。每一步单独看
都有理由，但整体上没有一条“做到哪里算完”的线。

结果是，工作看起来像是在乱撞：范围不断扩张，每个局部问题都显得同样重要，却回答不了一个更
基本的问题——这篇论文的主张是什么，支撑它的最小闭环是什么，哪个实验能把它关上，哪些东西
明确不做。没有这个顶层判断，实现就不知道在哪里停；而“再多做一点”看起来总比“决定不做什么”
安全。

张佳健学长在讨论中指出：这不是实现能力的问题，是目标没有定义清楚。目标不明确，就无法
排序，也无法判断一项工作是不是在为论文服务。这句话点中了这一阶段的要害。前面那些具体的
修补并不是白做，它们把“系统能成立”这件事做了出来；但如果继续沿着局部问题往下走，做得越多，
离“说清楚为什么做”就越远。

## 六、下一阶段：先顶层，再实现

下个阶段我准备把顺序倒过来：先做顶层设计，再回到实现。

1. 先用一句话定义目标：针对什么缺口，系统做什么，用什么证据成立。
2. 从这句话推出架构：语言、编译、调度三层各自承担哪一段论证，最小闭环是什么；组件不是因为
   “应该有”而存在，而是因为要承载某一条证据。
3. 再推出文章结构：每一章对应一个主张、一个实验和一组证据；“完成”由它要证明的东西定义，
   而不是由它实现了什么定义。
4. 同时明确不做什么：本轮的非目标、v1 的边界、留给后续的工作，都要先写下来，作为停下来的
   依据。
5. 最后才回到实现：只补叙事需要的缺口，不再见一个修一个。

这套从上而下的看法，也不只适用于这一篇文章。博士阶段的规划同样应该先回答研究问题、贡献和
几年的路线，再决定每年写什么代码；现在的系统是其中一件证据，不是目标本身。

这一阶段证明了链路可以成立；下一阶段要说明的是，这条链路为什么值得成立。

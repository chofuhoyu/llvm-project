# 从最小运行时到整程序：双周工作报告

> 范围：`caelum/20261108`（2026-11-03）至 `caelum/finish-roadmap-approach`（2026-11-15），共 87 个提交。

## 一、工作进展

本阶段从最小运行时出发，完善了 C++ 前端、算子边界与运行期入口。

1. 经初步审查，最小运行时已经能把放置决策移到运行期，但验收偏弱：GPU 用例只比对数值，设备编译失败会静默回退 CPU，数值正确无法区分算子实际运行位置。

2. 更新编译器前端与语义边界。C++ 从算子描述语言变成程序语言：整段程序经 ClangIR 进入 MLIR，算子按函数切分，宿主保留原符号与 C++ 签名，结果写到目的地；形状来自参数类型，annotation 表达算子与放置偏好。

3. 统一入口。skeleton++ 串起 clang++、cir-opt 与用户态driver（`mlir-skeleton-driver`）。该模块接收宿主与单元共存的模块，自己切分、改写调用、JIT 执行宿主，缓存未命中时按设备把单元编成目标代码，设备不可用或容量不足时回退 CPU。产物只含 CPU 实现与内嵌 IR，GPU 代码只在运行期产生。

4. benchmark 确定了第一批算子（softmax、layernorm、matmul、逐元素 add）。远端 GPU 主机上的三组测试通过。

## 二、成果汇报

一份 C++ 程序现在可以用一条命令编译并运行。宿主与算子单元在同一模块里共存，放置逐算子发生在运行期；同一份产物既可以按 CPU 单独运行，也可以被 driver 读回后补出 GPU 实现。编译期只负责把算子与 annotation 传下去，不再选择异构设备。

## 三、反思与下一阶段

这段工作暴露出我的问题：一直在往下做实现。运行时缺证据就补断言，断言的前提不成立就追到接口和上下文，文档对不上就再收文档；每一步都有局部理由，但没有一条“做到哪里算完”的线，整体上像是在乱撞。张佳健学长指出，根源不是实现能力，而是目标没有定义清楚。

下个阶段先把顺序倒过来：用一句话定义论文主张，从主张推出三层架构、最小闭环和章节结构，明确不做什么与停下来的依据，再回到实现，只补叙事需要的缺口。这套从上而下的看法也会用于梳理博士阶段的整体规划。这一阶段证明了链路可以成立，下一阶段要说明它为什么值得成立。

## 1. 概述

Skeleton Dialect 是叠加在 ClangIR / MLIR 技术栈上的一层结构化计算抽象。设计目标是让程序员通过 C/C++ 源码中的 annotation 把**偏好（preference）**与**计算模式（computation pattern）**向下传递，在 IR 层把偏好变成 target，最终利用 MLIR 基础设施完成 CPU / GPU 多目标代码生成。

本次变更在 `caelum/main` 之上新增了 **52 个文件、+3317 / −24 行**，包含：

- 一个完整的 MLIR 方言（`skeleton`）：`map` / `reduce` / `vector_add` / `yield` 四个 op，加一个 `preference` 属性。
- 五个 lowering / transform pass（skeleton → linalg → 按 preference 分拆 → 按 target 生成 CPU/GPU 代码）。
- CIR 前端两条路径的雏形（手动路径 + 半自动路径 stub）。
- 8 个单元测试 + 6 个集成测试（CPU + GPU）。

**总体结论**：这是一份**研究型 / 原型级**的实现。IR 层设计清晰、验证器写得比较扎实、lowering 链路的 CPU 部分基本自洽。

按「实现内缺陷 vs 愿景落差」划分后，真正需要优先处理的**实现内缺陷**有三处：① `preference-partition` 对链式 op 的正确性缺陷；② GPU 内存桥接的地址空间处理；③ 构建目录过时。而 CLAUDE.md 里设想的**全手动路径（CIR → Skeleton）尚未实现到位**（属性契约、纯函数转换、测试均属预期内的「愿景落差」，见 §6 阅读须知），这部分不是缺陷，是实现手动路径时需要先对齐的接口。

另外有两处**愿景自身的内部张力**（返回值 vs destination-passing、map-over-rows vs map-over-scalars），建议在动手实现手动路径前先拍板。

## 3. 变更内容与架构

### 3.1 分层架构

整个系统分四层，数据流自上而下：

```
C++ 源码（__attribute__((annotate(...))))
   │  clang -fclangir
   ▼
CIR（cir.func / cir.for / cir.call / cir.annotation）
   │  cir-call-to-skeleton（手动）/ cir-loop-to-skeleton（半自动，stub）
   ▼
Skeleton IR（skeleton.map / skeleton.reduce / skeleton.vector_add + pure_fn + preference）
   │  skeleton-pattern-merge（map+addf → vector_add）
   ▼
   │  skeleton-to-linalg（map→generic, reduce→reduce, vector_add→add，preference 转 discardable attr）
   ▼
Linalg（带 skeleton.preference 属性）
   │  skeleton-preference-partition（按 preference 把 linalg op 拆到独立 func.func，标 skeleton.target）
   ▼
func.func + skeleton.target（"CPU"/"GPU"）
   │  skeleton-target-lower（one-shot-bufferize + CPU→scf.for / GPU→scf.parallel + 设备内存桥接）
   ▼
   │  skeleton-finalize-memref-to-gpu（GPU 内存生命周期 → LLVM）
   ▼
MLIR 既有设施（scf→cf→llvm / gpu→nvvm）→ 可执行（mlir-runner JIT / CUDA runner）
```

### 3.2 各组件职责

**IR 层**（`mlir/include|lib/mlir/Dialect/Skeleton/IR/`）

| Op | 语义 |
|----|------|
| `skeleton.map` | 逐元素算子：`pure_fn`（FlatSymbolRefAttr）或可选 region body，二选一必填 |
| `skeleton.reduce` | 归约算子：二元结合函数 `(T,T)->T`，输出必须是 rank-0 标量 tensor |
| `skeleton.yield` | region 终止符，`HasParent<MapOp, ReduceOp>` |
| `skeleton.vector_add` | named op，pattern-merge 的产物，直接 lower 到 `linalg.add` |
| `#skeleton.preference<"CPU"|"GPU">` | `PreferenceAttr`，verifier 限定取值 |

**Transforms 层**（`mlir/lib/mlir/Dialect/Skeleton/Transforms/`）—— 5 个 pass：

1. `SkeletonToLinalg`：map（有 pure_fn 无 body）→ `linalg.generic`；reduce → `linalg.reduce`；vector_add → `linalg.add`。preference 以 discardable attribute 形式保留。
2. `SkeletonPatternMerge`：`map{pure_fn=@add}`（纯函数体是单个 `arith.addf`）→ `vector_add`。
3. `SkeletonPreferencePartition`：把带 `skeleton.preference` 的 linalg op 克隆进新的 private `func.func`，标 `skeleton.target`，原位替换为 `func.call`。
4. `SkeletonTargetLower`：先 one-shot-bufferize（含函数边界），再按 `skeleton.target` 决定 CPU（`scf.for`）还是 GPU（`scf.parallel` + `gpu.alloc`/`gpu.memcpy`/`gpu.dealloc` 设备内存桥接）。
5. `SkeletonFinalizeMemRefToGpu`：把 `gpu.memcpy` 等转成 LLVM，`gpu.alloc`/`gpu.dealloc` 留给下游 GPU 管线。

**CIR 前端**（`clang/lib/CIR/Dialect/Transforms/` + `clang/lib/CIR/CodeGen/`）：

- `CirCallToSkeleton`：全手动路径 —— 识别对 skeleton 辅助函数的调用，替换为 skeleton op。
- `CirLoopToSkeleton`：半自动路径 —— 目前只是对带 annotation 的循环发 warning（stub）。
- `CIRGenStmt.cpp` / `CIROps.td`：给 `cir.for`/`cir.while`/`cir.do` 增加 `annotations` 属性，把语句上的 `__attribute__((annotate(...)))` 落到循环 op 上。

## 6. 审查发现（按严重程度）

> **阅读前须知**：`CLAUDE.md` 是**开发愿景 / 预留接口的蓝图**，不是现状说明书。因此下面的发现分三类，价值不同：
>
> - **〔实现内缺陷〕**：已经写出来、且宣称能跑的那部分代码里的真实 bug —— 这是本次审查最该关注的部分。
> - **〔愿景落差〕**：愿景里设想了、但代码还没写到那一步的部分 —— 属于预期内，非缺陷，列出是为了说明「接口还差哪一块没接上」。
> - **〔愿景内部张力〕**：愿景本身存在两个相互冲突的设计选择（返回值 vs destination-passing、map-over-rows vs map-over-scalars），你实现全手动路径前需要先拍板 —— 这是我在愿景里发现的、可能你自己还没注意到的点。

| # | 分类 | 一句话 |
|---|------|--------|
| 6.5 | 实现内缺陷 | preference-partition 对链式 op 会生成非法 IR |
| 6.7 | 实现内缺陷 | GPU 内存桥接的地址空间处理可疑 |
| 6.9 | 实现内缺陷 | 构建目录过时，测试当前全部失败 |
| 6.1 | 愿景落差 | 前端读 `skeleton.op` 属性，愿景用 `annotate("skeleton_op")`，接口没对齐 |
| 6.2 | 愿景落差 | 纯函数还没从 `cir.func` 转成 `func.func` |
| 6.3 | 愿景落差 | 全手动路径尚未写测试 |
| 6.8 | 愿景落差 | 一个函数多 op / 非 skeleton 代码的处理还没做 |
| 6.4 | 愿景内部张力 | `skeleton_map(fn,a,b)` 返回值风格 vs `skeleton.map` 的 destination-passing |
| 6.6 | 愿景内部张力 | 「map 遍历行」的设想 vs 当前 block 参数是标量元素 |

### 🔴 严重（Critical）

#### 6.1 全手动路径的属性契约断裂，pass 实际是空转 〔愿景落差〕

[`CirCallToSkeleton.cpp:53`](clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L53)、[`:66`](clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L66) 读取的是 `skeleton.pure` / `skeleton.op` 这两个**直接属性**：

```cpp
if (func->hasAttr("skeleton.pure"))            // 期望直接属性
if (auto opAttr = func->getAttrOfType<StringAttr>("skeleton.op"))
```

但 CLAUDE.md 与 Passes.td 文档描述的前端写法是 `__attribute__((annotate("skeleton_op", ...)))`，它经过 CIR codegen 只会产生 `annotations = [#cir.annotation<"skeleton_op", ["map"]>]` 这样的 **`cir.annotation` 数组属性**，而不是名为 `skeleton.op` 的属性。

我全局搜索了 `skeleton.op` / `skeleton.pure` 的生产点，结果**只有消费点、没有生产点**——没有任何代码把 `annotate("skeleton_op")` 转成 `skeleton.op` 属性。因此 `collectSkeletonOpDecls` 永远返回空，pass 在 [`CirCallToSkeleton.cpp:283`](clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L283) 直接 `return`，**整个手动路径实际是 no-op**。

> 注意：连命名都不一致——注解名是 `skeleton_op`（下划线），属性名是 `skeleton.op`（点号）。

#### 6.2 纯函数未从 `cir.func` 转换为 `func.func`，生成的 IR 无法通过验证 〔愿景落差〕

即使 6.1 修好，`skeleton.map` 的 `pure_fn` 通过 `SymbolTable::lookupNearestSymbolFrom<func::FuncOp>` 解析（[`SkeletonOps.cpp:38`](mlir/lib/Dialect/Skeleton/IR/SkeletonOps.cpp#L38)），要求 `pure_fn` 指向一个 `func.func`。但 [`CirCallToSkeleton.cpp`](clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp) 只重写了**包裹函数**（`vec_add`），从未把带 `skeleton.pure` 的纯函数（`my_add`，仍是 `cir.func`）转成 `func.func`。结果是 `pure_fn @my_add not found` 验证失败。

#### 6.3 全手动路径零测试，无法证明其可用性 〔愿景落差〕

`find` + `grep` 确认：仓库里**不存在**任何 `cir-call-to-skeleton` 测试文件。作为 CLAUDE.md 宣称的「全手动路径」这一核心功能，它既无单元测试也无端到端测试，且因为 6.1/6.2 的问题，它实际上从未真正端到端跑通过。

### 🟠 重要（Major）

#### 6.4 手动路径的 header API 与 lowering 语义不匹配 〔愿景内部张力〕

文档里辅助函数签名是函数式风格，输出是返回值：

```cpp
std::vector<float> skeleton_map(auto fn, const std::vector<float>& a, const std::vector<float>& b);
```

但 [`CirCallToSkeleton.cpp:313`](clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L313) 按 destination-passing 风格解释调用：

```cpp
unsigned numArgs = callOp.getNumOperands();  // fn,a,b = 3
unsigned numDataOps = numArgs - 1;           // 2
unsigned numInputs = numArgs - 2;            // 1  ← 把 b 当成输出！
```

`lowerMapCall` 里 [`memrefArgs[info.numInputs]`](clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L217) 被当作 `outs`。对 `skeleton_map(fn, A, B)` 而言，`B` 会被错误地当作输出缓冲区覆盖，语义错误。要么 header 改成 destination-passing（显式 out 参数），要么 lowering 改成从返回值构造 out，二者当前是矛盾的。

#### 6.5 preference-partition 对链式 producer-consumer 有正确性缺陷 〔实现内缺陷〕

[`SkeletonPreferencePartition.cpp:96`](mlir/lib/Dialect/Skeleton/Transforms/SkeletonPreferencePartition.cpp#L96) 的 outline 循环里，`entry.inputs` 在 Phase 1 就已经被快照。当两个带 preference 的 linalg op 链式依赖（`%0 = matmul1(..)`, `%1 = matmul2(%0, ..)`）时：

1. 先处理 producer `matmul1`，执行 `op->replaceAllUsesWith(call1.getResults())`，把 consumer `matmul2` 的操作数从 `%0` 替换成 `call1` 的结果。
2. 再处理 consumer `matmul2` 时，`entry.inputs` 里存的还是**旧的 `%0`**（已 dangling），`mapper` 映射旧值 → block arg，但 `matmul2` 实际操作数已是 `call1` 结果，clone 后新函数体引用了一个**函数外部的值**，产生非法 IR。

现有测试（`skeleton-preference-partition.mlir` 的 `test_mixed`）三个 matmul 都用函数入参、互不依赖，因此没触发。需要补一个链式用例，或改用「先按拓扑序 / 对快照值做 use 追踪」的 outline 策略。

#### 6.6 map/reduce 的 region 语义与文档/设计意图不符 〔愿景内部张力〕

文档（[`SkeletonOps.td:37`](mlir/include/mlir/Dialect/Skeleton/IR/SkeletonOps.td#L37) 与 CLAUDE.md）举的嵌套例子是「map 遍历矩阵行、region 内放 reduce 对每行归约」，body block 参数是行切片 `tensor<?xf32>`：

```mlir
^bb0(%row: tensor<?xf32>, %init: tensor<f32>):
```

但 [`MapOp::verify`](mlir/lib/Dialect/Skeleton/IR/SkeletonOps.cpp#L130) 校验 block arg 类型等于**元素类型**（`getElementType()` = `f32`），不是切片类型。`skeleton-ops-valid.mlir` 里唯一的嵌套用例用的也是标量 body（`^bb0(%row: f32, %init: f32)`），并无可复用的嵌套 reduce。

**结论**：CLAUDE.md 描述的「region 嵌套组合算子（map 内嵌 reduce 做逐行归约）」在现有验证器和 lowering 下**不可实现**。文档里的嵌套示例按当前 verifier 会直接验证失败。

#### 6.7 GPU 内存桥接的地址空间处理可疑 〔实现内缺陷 · 实测通过〕

[`SkeletonTargetLower.cpp:131`](mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L131) 创建 `gpu.alloc` 时用 `MemRefType::get(shape, eltType)`，**没有显式带 GPU 地址空间**（`#gpu.address_space<...>`），随后又 `memref.cast` 回宿主 memref 类型：

```cpp
auto allocType = MemRefType::get(shape, eltType);   // 默认地址空间 0，未显式标注设备内存
auto allocOp = gpu::AllocOp::create(builder, loc, allocType, ...);
auto casted = memref::CastOp::create(builder, loc, entry.hostMemrefType, allocOp.getMemref());
```

**实测结论（2026-08-21）**：`test-skeleton-matmul-gpu.mlir` 在 RTX 5060 Ti 上端到端通过，数值正确（`[[19,22],[43,50]]`），说明当前写法在现有 MLIR GPU 管线下**能正常工作**——地址空间大概率由下游 `gpu-lower-to-nvvm-pipeline` 的 memory-space 分配环节补全。这段是 8f4fdf5、2393f64、da9bf86、00afe3f 多次迭代的产物，说明作者在此处反复打转。

**遗留风险（不是 bug，是健壮性）**：`gpu.memcpy` 的 H↔D 方向靠源/目的 memref 的地址空间推断，这里两个 memref 都是默认空间，方向判定依赖下游的隐式约定而非显式语义。建议将来花时间搞清楚「为什么能工作」，避免升级 MLIR 或换 GPU 架构（如未来 arch 默认值变化）时踩坑。

#### 6.8 多 op / 非 skeleton 代码的函数体被静默丢弃 〔愿景落差〕

[`rewriteToStandardFunc`](clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L158) 创建一个**空** `func.func`，只塞入单个 skeleton op。若一个 `cir.func` 里有多个 skeleton 调用，会生成**多个同名 func.func**（符号冲突）；若还有非 skeleton 语句，则**被静默丢弃**（错误代码生成）。当前实现隐式假设「一个函数只包一个 skeleton 调用」，但没有校验或错误处理。

#### 6.9 构建目录过时/损坏，测试当前全部失败 〔实现内缺陷 · 已解决〕

实测 `build/bin/mlir-opt` 不含 skeleton pass（运行 `llvm-lit` 报 `Unknown command line argument '-skeleton-preference-partition'`，**7/7 单元测试失败**）。进一步检查：

## 1. 一张图看完整个项目（数据流）

数据从上往下流，每一行箭头代表一次 IR 到另一种 IR 的翻译。方括号里是**这个 pass 的 CLI 开关名**，括号里是实现它的 `.cpp` 文件：

```
C++ 源码（__attribute__((annotate(...)))）
  │ clang -fclangir
  ▼
CIR（cir.func / cir.call / cir.for / cir.annotation）          ← clang/lib/CIR/
  │  [cir-call-to-skeleton]  手动路径                              CirCallToSkeleton.cpp
  │  [cir-loop-to-skeleton]  半自动（目前只发 warning）             CirLoopToSkeleton.cpp
  ▼
Skeleton IR（map / reduce / vector_add / yield + preference）  ← mlir/Dialect/Skeleton/
  │  [skeleton-pattern-merge]  map{addf} → vector_add              SkeletonPatternMerge.cpp
  │  [skeleton-to-linalg]      map→generic, reduce→reduce,
  │                            vector_add→add                      SkeletonToLinalg.cpp
  ▼
Linalg（op 上挂着 skeleton.preference discardable 属性）
  │  [skeleton-preference-partition]  按 preference 拆 op 进独立 func.func，标 skeleton.target
  ▼                                                                SkeletonPreferencePartition.cpp
func.func + skeleton.target（"CPU" / "GPU"）
  │  [skeleton-target-lower]   bufferize + CPU→scf.for / GPU→scf.parallel + 设备内存桥接
  │  [skeleton-finalize-memref-to-gpu]  GPU 侧 memref 生命周期 → LLVM
  ▼                                                                SkeletonTargetLower.cpp
                                                                   SkeletonFinalizeMemRefToGpu.cpp
MLIR 既有设施（scf→cf→llvm / gpu→nvvm）→ 可执行
```

**读这张图时抓住 5 个概念：**

1. **三层 IR 接力**：CIR（Clang 的）→ Skeleton（本项目新造的方言）→ Linalg（MLIR 现成的）。每两层之间正好一个 pass 做翻译。
2. **preference 是贯穿全链路的"便签"**：Skeleton 方言属性 → to-linalg 转 discardable 属性 → partition 按它拆函数 → target-lower 按 `skeleton.target` 选 CPU/GPU。一条线到底（详见 §2 契约地图）。
3. **pure_fn 机制**：op 用 `pure_fn = @name` 引用一个**命名函数**，lowering 时把那个函数的**函数体 clone 进 linalg 的 region**。这是本项目的核心设计——纯函数是叶子节点，被骨架算子引用。
4. **两套前端路径**：手动（辅助函数调用 → op）已写但**没接上**，半自动（循环注解 → op）还是 stub。这是"继续写"的主战场（§10）。
5. **每个 pass 都有一个 .mlir 测试**：测试就是最好的"输入→输出"说明书。读 pass 时对照测试读，比纯看代码快得多。

## 2. 一张图看懂全链路接口（谁生产谁消费）

这张表是**继续往下写**最需要的地图。它回答一个问题：每一层之间靠什么属性/符号衔接，这个属性**在哪里被生产、在哪里被消费**。凡是"有消费点、没生产点"或"生产了、没消费"的，就是断链处。

| 契约项 | 形态 | 生产点 | 消费点 |
|--------|------|--------|--------|
| `#skeleton.preference<"CPU"/"GPU">` | `PreferenceAttr` | 手写 skeleton op /（规划中）前端 annotation | `SkeletonOps.cpp:24` verifier 限取值 |
| `skeleton.preference` | discardable attr（挂在 linalg op） | `SkeletonToLinalg.cpp:97` `setDiscardableAttr` | `SkeletonPreferencePartition.cpp:63` `getDiscardableAttr` |
| `skeleton.target` | `StringAttr`（挂在 func.func） | `SkeletonPreferencePartition.cpp:122` | `SkeletonTargetLower.cpp:55` 选 CPU/GPU；`SkeletonFinalizeMemRefToGpu.cpp:50` 判断是否激活 |
| `pure_fn` | `FlatSymbolRefAttr`（指向 func.func symbol） | 手写 skeleton op /（规划中）前端 | `SkeletonOps.cpp:35` 查签名；`SkeletonToLinalg.cpp:48` clone 函数体 |
| `skeleton.op` / `skeleton.pure` | 直接属性（挂在 cir.func） | **无生产点（断链）** | `CirCallToSkeleton.cpp:50/63` 收集 |
| `annotations` | `ArrayAttr` of `cir.annotation`（挂在 cir.for/while/do） | `CIRGenStmt.cpp:90` `attachLoopAnnotations` | `CirLoopToSkeleton.cpp:45`（只发 warning） |

**这张表里藏着两处断链，读懂它们就懂了"继续写"的方向：**

1. **手动路径断在 `skeleton.op`/`skeleton.pure`**：C++ 的 `__attribute__((annotate("skeleton_op", ...)))` 经过 CIR codegen，落到 IR 上的是 `annotations = [#cir.annotation<"skeleton_op", ["map"]>]` 这个**数组属性**，而不是名为 `skeleton.op` 的**直接属性**。`CirCallToSkeleton` 只读后者 → `opDecls` 恒空 → pass 空转。要接上，缺一个「把 `cir.annotation` 翻译成 `skeleton.op`/`skeleton.pure` 直接属性」的环节。

2. **半自动路径断在「只消费不产出」**：`annotations` 已经由 `CIRGenStmt.cpp` 生产了、也落到循环 op 上了，但 `CirLoopToSkeleton` 读到之后**只发 warning 不产出 skeleton op**。这一条的生产端是通的，缺的是消费端把它变成 op 的那段分析代码。

> 一句话记住：**前端两条路径都卡在「生产 → 消费」的衔接上**。后端（Skeleton → Linalg → target）的链是完整的、能端到端跑的。

### 带着问题读

- **map** 有 `ins`（可变个）、`outs`（1 个，参数名 `init`）、`result`（1 个）。verifier 里 `init` 和 `result` 之间要满足什么关系？（`initType != resultType` → 报错；这是**完整 RankedTensorType 比较**，含 rank/shape/元素类型）
- **reduce** 对 init rank 有什么要求？（必须 rank-0 标量）对 init 元素类型呢？（必须 == 输入元素类型）
- **yield** 是谁约束它只能出现在哪？（`HasParent<"MapOp, ReduceOp">`）
- **vector_add** 为什么叫 "named op"？它和 map 比，少了哪个自由度？（它把「任意纯函数」固定成了「加法」，且只能 1D）
- `verifyPureFnSignature` 从哪找 `pure_fn` 指向的函数？（`SymbolTable::lookupNearestSymbolFrom<func::FuncOp>`）它检查了 4 件事：参数个数、每个参数类型、结果个数（==1）、结果类型。
- `pure_fn` 和 `body` region 是什么关系？（二选一必填）

> **注解（2026-08-27）**：文档预期是「二选一」，但代码原实现只拦「两个都没有」：`if (!hasPureFn && !hasBody)`（[`SkeletonOps.cpp:83`](../../mlir/lib/Dialect/Skeleton/IR/SkeletonOps.cpp#L83)），所以 **hybrid（`pure_fn` + `body` 同时存在）能过验证**——而它没有语义：pattern-merge 与 to-linalg 都以 `body` 为空为匹配前提（[`SkeletonPatternMerge.cpp:73`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonPatternMerge.cpp#L73)、[`SkeletonToLinalg.cpp:41`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonToLinalg.cpp#L41)），hybrid 不匹配任何 pattern，会残留到 LLVM conversion 才报错，其 `pure_fn` 是永不读取的死属性。本次已把条件改为 `hasPureFn == hasBody`（exactly one），并补了 hybrid 反例测试。

### 读的时候注意（先自己想）

1. **文档例子 vs verifier 的矛盾**：[`SkeletonOps.td:42`](../../mlir/include/mlir/Dialect/Skeleton/IR/SkeletonOps.td#L42) 的嵌套例子，block 参数是**行切片 tensor**（`^bb0(%row: tensor<?xf32>, ...)`）。但 [`SkeletonOps.cpp:127-137`](../../mlir/lib/Dialect/Skeleton/IR/SkeletonOps.cpp#L127) 的 `MapOp::verify` 检查 block 参数类型 == **元素类型**（`f32`）。这两个对不上。→ 这是「愿景 vs 实现」的第一处裂缝：CLAUDE.md 设想的「map 内嵌 reduce 逐行归约」在当前 verifier 下**不可表达**。

2. **ReduceOp 注释 vs 代码**：[`SkeletonOps.cpp:165`](../../mlir/lib/Dialect/Skeleton/IR/SkeletonOps.cpp#L165) 的注释说「Input must be at least 1D」，但往下看代码——**只检查了 init rank == 0，没检查输入 rank**。rank-0 输入也会通过验证。

3. **MapOp 不查 input vs init 的 rank/shape**：它查了 `initType == resultType`，但**没查 input 和 init 之间 rank/shape 是否一致**（`tensor<2x3xf32>` 输入配 `tensor<2xf32>` init，能过验证）。这个不查，站 2 的 `SkeletonToLinalg` 会按 result 的 rank 生成 indexing map，然后错位。

4. **VectorAddOp 要求全 1D**：[`SkeletonOps.cpp:225`](../../mlir/lib/Dialect/Skeleton/IR/SkeletonOps.cpp#L225) 强制所有操作数 rank == 1。记下这条，站 2 的 pattern-merge 会踩它。

## 2. pattern-merge 补强：防误合并（rank 检查）+ 放宽 isAddFn（识别更多加法形态）

`MergeMapAddToVectorAdd` 的判定逻辑（[`SkeletonPatternMerge.cpp:36-104`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonPatternMerge.cpp#L36)）有两个方向要补，都落在 `isAddFn` + `MergeMapAddToVectorAdd` 同一段代码上，放同一条、一起做：

**防守：不查 rank，会产出过不了验证的 IR。** 它只查「输入个数=2、有 pure_fn、无 body、isAddFn」，**不查 rank**（[`SkeletonPatternMerge.cpp:77-79`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonPatternMerge.cpp#L77) 的 TODO 自己点破）。一个 **2D** 的 `map{pure_fn=@add}` 会被 merge 成 `vector_add`，而 `VectorAddOp::verify` 强制全 1D（[`SkeletonOps.cpp:217`](../../mlir/lib/Dialect/Skeleton/IR/SkeletonOps.cpp#L217)）→ 产出一个**过不了验证的 IR**。修法：merge 前查 operand rank == 1（顺带查元素类型）；补一个 2D 反例测试。

**进攻：`isAddFn` 对 pure_fn 的形态要求过于严格，该认的加法放跑了。** `isAddFn`（[`SkeletonPatternMerge.cpp:36-63`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonPatternMerge.cpp#L36)）用**精确结构匹配**判定「纯函数是加法」：恰好 1 block、恰好 2 op、第一个 op 必须是 `arith.addf` 且操作数**精确等于**块参数 0/1（顺序敏感）、terminator 是 return 且**精确返回** addf 结果。任何偏差都识别不出：

- 参数顺序反了（`addf %b, %a`——加法满足交换律，语义等价）→ 不 merge；
- 函数体多一条指令（哪怕无关）→ 不 merge；
- 多 block 函数体（if/else）→ 不 merge（clone 还会静默丢弃多出的 block，见 TODO-3）；
- 整数加法 `addi` → 不 merge（named op 目前只有 vector_add，`mulf` 不 merge 是预期行为；`addi` 是覆盖缺口）。

失败**不是错误**——只是不 merge，`skeleton.map` 走通用 skeleton-to-linalg。这是「表达能力 / 优化机会」问题，不是正确性问题。修法方向：从「精确 op 计数 + 操作数顺序」改成**子图 / 根 op 匹配**——根 op 是 `arith.addf`（接受交换律）+ terminator 返回其结果，容忍无关指令；顺带纳入元素类型检查、`addi` 判定（若有 `vector_addi` 目标）。配套补测试：`addf %b, %a`、含多余指令的函数体、f64 加法、`addi`。

> 关联：这条的「严格」与前端的 pure_fn 识别是同一问题的两面——前端 `extractPureFnRef` 也只认 `get_global` 直接引用（见 TODO-8 补录 2/3），两者共同决定「程序员实际写出来的代码能走多远」。排在 ① 之后：rank 检查直接消费 ① 定义的 verifier 边界（先定边界、再让 merge 遵守），isAddFn 放宽与其同代码顺带一起做。

## 3. 函数体 clone：多 block 支持（现在会静默丢弃）

`ConvertMapOp`（[`SkeletonToLinalg.cpp:76-91`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonToLinalg.cpp#L76)）和 `ConvertReduceOp`（[`SkeletonToLinalg.cpp:132-144`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonToLinalg.cpp#L132)）都只 clone **entry block**，terminator 硬 `cast<func::ReturnOp>`。pure_fn 里有 if/else（多 block）时，多出来的 block 被**静默丢弃**——最危险的一种失败：不报错，结果不对。

修法二选一：**拒绝**多 block 函数体（明确报错），或**正确内联**整个函数体。当前「静默丢」不可接受。

## 4. preference-partition：链式依赖支持 + 重复 outline 去重

Phase 1 把 `entry.inputs/outputs` 快照成 **Value**（[`SkeletonPreferencePartition.cpp:78-79`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonPreferencePartition.cpp#L78)），Phase 2 先处理 producer 时 `replaceAllUsesWith` 把 consumer 的操作数换成新 call 结果，等处理 consumer 时快照里的旧 Value 已经 dangling → 生成非法 IR。**只对「互不依赖的 op」安全**。现有 `test_mixed` 的三个 matmul 互不依赖，没触发。

修法：按拓扑序处理（先 producer 后 consumer 时用 use 追踪拿最新值），或 Phase 2 重建 operands 而不是用 Phase 1 快照。补一个链式用例测试（两个 matmul 一个消费另一个的输出）。

**重复 outline 不去重**（同一 pass 的另一个边界，2026-08-29 实测确认）：同一函数内多个带 preference 的 op，即使 preference、op 类型、操作数形态完全相同，也会各自 outline 成独立函数（函数名靠 idx 区分，如 `GPU_matmul_0` / `GPU_matmul_1`），**不做去重**。后续 `skeleton-target-lower` 对每个函数各生成一份相同的 `scf.parallel` 代码，GPU 桥接（`gpu.alloc` / `gpu.memcpy` / `gpu.dealloc`）也是两套完整独立的——重复但正确。原因：partition 无条件一 op 一函数，idx 只用于名字区分；下游也没有等价函数合并 pass（`symbol-dce` 只删无引用的，这两个函数都有 call 引用，删不掉）。修法方向：outline 时按「preference + op 形态 + 操作数集合」去重，相同则复用已有函数；或留给未来调度器归并同形态调度单元。实测佐证：两个 GPU matmul 输入，partition 产出 `GPU_matmul_0` / `GPU_matmul_1`，target-lower 后两份相同循环 + 两套完整桥接。

## 5. target 属性类型化：skeleton.target 用强类型 attr，而不是裸 StringAttr

`skeleton.target` 是 partition outline 时动态挂到 func.func 上的**裸 StringAttr**：key 是字符串 `"skeleton.target"`，值也是字符串（`"GPU"` / `"CPU"`）。生产端 [`SkeletonPreferencePartition.cpp:121-122`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonPreferencePartition.cpp#L121) `setAttr("skeleton.target", StringAttr::get(ctx, entry.preference))`，消费端全靠**字符串名 + 字符串值**判断：

- [`SkeletonTargetLower.cpp:54`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L54) 按名字 `getAttrOfType<StringAttr>("skeleton.target")` 找函数；
- [`SkeletonTargetLower.cpp:66`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L66) 用 `attr.getValue() == "GPU"` 分派；
- [`SkeletonTargetLower.cpp:226-238`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L226) 再对 `"CPU"` / `"GPU"` 做 `==` 比较，未知值只发 warning；
- [`SkeletonFinalizeMemRefToGpu.cpp:50`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonFinalizeMemRefToGpu.cpp#L50) 同款字符串判断。

三个问题，都是「对 attr 失去完整控制」的表现：

1. **值无类型约束**：`"GPU"` 只是裸字符串，`"TPU"`、拼写错误都能挂上去，到 target-lower 消费时才被 warning 吞掉。对比 `PreferenceAttr` 有 verifier 限定 CPU/GPU（[`SkeletonDialect.cpp:23-30`](../../mlir/lib/Dialect/Skeleton/IR/SkeletonDialect.cpp#L23)），target 却没有。
2. **key 可能同名**：属性名是字符串键，任何代码（含非 skeleton 的 pass、手写 IR）都能往 func.func 挂同名同型属性，消费端 `getAttrOfType<StringAttr>("skeleton.target")` 只认「名 + 内建类型」，无法区分真伪——`skeleton.target` 会被当成「恰好叫这个名字的字符串」，而不是「skeleton 方言声明的属性」。
3. **魔法字符串散落三处消费点**：`== "GPU"` 没有单一真源，枚举取值要改时满文件搜。

修法方向（与 preference 同源，成本低）：**把 target 的值从 StringAttr 换成 skeleton 方言的 `PreferenceAttr`**——它已存在、verifier 已限定 CPU/GPU、已有 mnemonic 和 assemblyFormat。生产端改 `PreferenceAttr::get(ctx, ...)`，消费端改 `dyn_cast<PreferenceAttr>` + 按 `.getValue()` 模式匹配。或更进一步定义专用 `#skeleton.target<"GPU">` attr，给未来调度器要表达的「软约束 / fallback 策略」留字段（与 TODO-12 preference 软约束化呼应）。连带更新三份测试 CHECK：[`skeleton-preference-partition.mlir:14/32/59/64`](../../mlir/test/Dialect/Skeleton/skeleton-preference-partition.mlir#L14)、[`skeleton-target-lower.mlir:5/21`](../../mlir/test/Dialect/Skeleton/skeleton-target-lower.mlir#L5)、[`skeleton-finalize-memref-to-gpu.mlir:21`](../../mlir/test/Dialect/Skeleton/skeleton-finalize-memref-to-gpu.mlir#L21)。

## 6. target-lower：GPU 桥接的三个假设

- **动态 shape 跳过桥接**（[`SkeletonTargetLower.cpp:123-132`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L123)）：`emitWarning` 后 `continue`，host memref 直通 GPU，kernel 会读写 host 内存——静默降级成错误代码。
- **设备 memref 类型重建丢信息**（[`SkeletonTargetLower.cpp:135-142`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L135) + TODO）：`MemRefType::get(shape, eltType)` 没带 GPU 地址空间、丢了 host layout。为什么现在能跑？**两个假设恰好同时成立**，任一被打破就出事：① 地址空间——`gpu.alloc` verifier 不强制（[`GPUDialect.cpp:2295`](../../mlir/lib/Dialect/GPU/IR/GPUDialect.cpp#L2295)），memory space 0 → NVVM generic，而 NVPTX 的 generic 恰好覆盖 global（[`NVGPUToNVVM.cpp:1716-1719`](../../mlir/lib/Conversion/NVGPUToNVVM/NVGPUToNVVM.cpp#L1716) 注释明说）——是**碰巧**，不是「下游补地址空间」，换 ROCm 就暴露；② layout——host 数据恰好全 identity，`gpu.memcpy` 裸字节拷贝才正确（[`GPUToLLVMConversion.cpp:1142-1163`](../../mlir/lib/Conversion/GPUCommon/GPUToLLVMConversion.cpp#L1142)）；host 若带 concrete 非 identity layout，`ConvertMemcpyOpToGpuRuntimeCallPattern` 的 `isConvertibleAndHasIdentityMaps` 会拒绝转换 → **显式失败**（`failed to legalize gpu.memcpy`，实测，[`GPUToLLVMConversion.cpp:1133-1137`](../../mlir/lib/Conversion/GPUCommon/GPUToLLVMConversion.cpp#L1133)）。修法：`allocType` 从 `hostMemrefType` 推导（保留 layout + 地址空间）。
- **单输出假设**（[`SkeletonTargetLower.cpp:208-221`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L208)）：硬编码替换 `call.getResult(0)`；多个可写 memref、多结果都会静默丢 copy-back。

三者都是 GPU 路径的边界，CPU 路径（scf.for）没有。支持动态 shape 或多输出时改 Phase A/B 的 bridge 逻辑。排在 ⑤ 之后：修法不如 ⑤ 明确，且需要 GPU 环境验证。

## 7. 返回值 vs destination-passing：动手前先拍板

文档里的辅助函数是**返回值风格**（`skeleton_map(fn, A, B)` 返回新向量），但 `lowerMapCall` 的 `numInputs = numArgs - 2`（[`CirCallToSkeleton.cpp:329`](../../clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L329)）把 `B` 当成**输出缓冲区**——`B` 会被覆盖，语义错了。**接手动路径之前必须先拍板**：API 是返回新张量还是原地写。这决定 `rewriteToStandardFunc` 的参数布局和 lowering。

## 8. 前端手动路径：补上 skeleton.op / skeleton.pure 的生产端

**断链证据（完整推理链）**：C++ 的 `__attribute__((annotate("skeleton_op", ...)))` 经过 CIR codegen 落到 `annotations = [#cir.annotation<...>]` 数组属性（[`CIRGenStmt.cpp:88-101`](../../clang/lib/CIR/CodeGen/CIRGenStmt.cpp#L88)），而 `CirCallToSkeleton::collectSkeletonOpDecls` 读的是**名为 `skeleton.op` 的直接属性**（[`CirCallToSkeleton.cpp:63`](../../clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L63)）。`skeleton.op` / `skeleton.pure` **只有消费点、没有生产点**（§2 契约地图）→ `opDecls` 恒空 → pass 在 297 行直接 return。**整个手动路径是 no-op。**

接法二选一：把 `annotations` 里的 `cir.annotation` 翻译成 `skeleton.op` / `skeleton.pure` 直接属性（新增一个生产环节），或改 `CirCallToSkeleton` 直接读 `cir.annotation`。

连带问题：`rewriteToStandardFunc` 是有损重建（[`CirCallToSkeleton.cpp:161-165`](../../clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L161) TODO 已点明）——指针参数 → `memref<?xT>`（shape 丢）、函数体整个丢弃、一个函数多个 skeleton 调用会生成同名 func.func（符号冲突）。接上前先想清楚「有损」能不能接受。

## 10. 行级嵌套：map body 内嵌 reduce（要不要支持——先讨论）

**现状（矛盾的复述）**：两种 map 语义在代码里互相冲突。

- 文档例子（[`SkeletonOps.td:35-46`](../../mlir/include/mlir/Dialect/Skeleton/IR/SkeletonOps.td#L35)）和 CLAUDE.md 愿景：map 的 body 在**行切片**上执行，body 内嵌 `skeleton.reduce` 表达「对矩阵每一行做归约」。input 是 2D、output 是 1D（降维）。
- 当前 verifier（[`SkeletonOps.cpp:122-133`](../../mlir/lib/Dialect/Skeleton/IR/SkeletonOps.cpp#L122)）只允许 body 参数 == **元素类型**（`f32`）——即元素级 map，body 一次处理一个标量。

两种语义下 body 参数类型必然不同（`tensor<?xf32>` vs `f32`），verifier 硬编码成后者，前者就永远报错。**「行级嵌套」在当前实现里不可表达。**

**两种语义模型（先拍板选哪个）**：

1. **元素级 map（现状）**：body 每个元素跑一次，ins/outs 逐元素对应，shape 不变。语义干净，pure_fn 已经覆盖了这个用途。
2. **行级/块级 map（愿景）**：body 每行跑一次，body 输入是行切片张量，输出可降维。region 才真正有了「组合算子」的意义。

**要不要支持？我的倾向：值得做，但先定语义、后写代码，且排期靠后（等前端接上之后再动，否则没人用）。**

- **支持的理由**：这是「region 组合骨架算子」的唯一展示，是 CLAUDE.md「可组合性 ⇒ 可自然切分」主张的关键证据。没有它，region 只能做纯标量计算，和 pure_fn 的功能重叠，region 机制名存实亡。
- **延后的理由**：当前没有真实用例（前端两条路径都是 no-op，不会产生 body）；element-wise map + 显式 reduce 能表达绝大多数计算，只是不「结构化成行」；改动横跨 verifier / to-linalg lowering / pattern-merge 三处；降维语义在 linalg 里怎么表达没有现成答案。

**如果支持，要拍板的决策点**：

1. **切哪根轴**：行切片按 dim 0 切？多个 input rank 不同怎么办（`tensor<?x?xf32>` 配 `tensor<?xf32>`）？
2. **body 签名**：block 参数 = [每个 input 的一个切片, init 切片]？切片类型 rank = input.rank − 1？切片长度怎么和 output 对应？
3. **降维怎么落到 linalg**：linalg 的「逐行归约」一般用 reduction iterator，但 map 的 element-wise 语义没有 reduction 轴。现有 `ConvertMapOp` 看到 body 直接 `failure()`（[`SkeletonToLinalg.cpp:39`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonToLinalg.cpp#L39)），body 嵌套需要**新写 lowering**，不能走 clone 函数体的老路。
4. **与 pure_fn 的混合模型**：文档例子里 body 内嵌的是 `reduce{pure_fn=@my_sum}`——「组合容器 + 纯函数叶子」的混合，这个模型要明确写进文档。
5. **pattern-merge 的 rank 假设**：行级 body 天然是 2D 输入，`vector_add` 是 1D-only。merge 现在靠 `getBody().empty()` 排除了 body 分支（[`SkeletonPatternMerge.cpp:72`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonPatternMerge.cpp#L72)），但纯函数叶子路径仍要防 2D 误合并（见 TODO-2）。

**落地路径（如果做，TDD 顺序）**：

1. 先写一个行级嵌套的 `.mlir` 测试当规格（预期 IR 形态 = 外循环 × 行内 reduce）。
2. 改 verifier：body 参数类型放宽，定义切片语义。
3. 写 `ConvertMapOp` 的 body 分支（或新 pattern）：把「外 map × 内 reduce」展开成 linalg。
4. 补 merge 的 rank 检查（与 TODO-2 合并）。
5. 跑集成测试验证数值。

> 排 ⑩ 的理由：这是文档里最早写下的一条，但按执行顺序它该靠后——①–⑨ 先保证「前端能真正产生 body」「后端 IR 稳定」，它才有真实用例和可验证的基础。等 ⑧ 前端接上后再回头讨论要不要做。

## 11. 调度器（核心目标，规划中，无代码）

CLAUDE.md 的核心目标：**充分利用异构算力**。独立于现有 pipeline 的用户层调度器——与 clang 并列的独立 driver（LLVM 概念的 driver），**不是 MLIR pass**。要点：纯函数无副作用 ⇒ 切分安全；切分粒度动态、随设备动态求最优解；静态切分 + 动态决策；preference 是软约束。

当前实现（partition + target-lower）是**静态、按 preference 写死**的形态，是调度器的雏形/前置，离「动态调度」还远。这是整个愿景的终点，现阶段没有任何代码，也不该急——先把单 target 路径和前端做扎实。

## 12. preference 软约束化（现状 vs 愿景）

愿景：preference 是**软约束**——调度器尽量尊重程序员意图；硬件不满足则改派其他设备，或回退 CPU。现状：partition / target-lower 把它当**硬目标**用（CPU→scf.for，GPU→scf.parallel，写死）。

这是「现状 vs 愿景」的差距，也是未来独立调度器要解决的核心问题。等调度器立项时一起做，现在不用动——但写代码时别把 preference 的「硬目标」行为焊死（比如别依赖它做正确性判断）。

# 20260907：manual-path 提交的阅读顺序

这次审的是 commit `294be6380fa7`「Add manual-path C++ header and C++-to-run CPU e2e tests」（已被 `git reset --soft` 摊回暂存区，还没重新提交）。它补了三样东西：一个给用户 include 的 C++ 头文件、`cir-call-to-skeleton` 里删模块级 CIR 属性的改动、以及配套的一组测试。下面是从哪看起的顺序。

## 第 1 步：看 skeleton-manual-path.cpp 的注释（1-36 行）

这个文件是整条提交的说明书。它用 `// CHECK-*` 写死了 pass 该产出什么，先看它，后面所有代码都有了对得上号的东西。留意三段 CHECK：

- 纯函数 `my_add` / `my_sum` → `func.func @_Z6my_addff(...) -> f32`，函数体变成 `arith.addf`；
- map 的宿主 `vec_add` → `(memref<?xf32>, memref<?xf32>) -> tensor<?xf32>`，多出 `to_tensor` / `tensor.dim` / `tensor.empty`；
- reduce 的宿主 `sum_all` → `(memref<?xf32>) -> tensor<f32>`（标量，没有 `dim`）。

这三段正好对应 CirCallLowering.cpp 里的三处机制：纯函数体转 arith、map 的输出形状、reduce 塌成 rank-0。

## 第 2 步：看 dropCirModuleAttrs（CirCallToSkeleton.cpp 51-60 行）和它被调用的位置（168 行）

这是这条提交里唯一的产品逻辑改动。要懂它，先回答一个问题：module 上到底有哪些 `cir.*` / `dlti.*` 属性，留着为什么不行？不用凭空想，直接编真实 CIR 出来看：

```bash
./build/bin/clang -cc1 -std=c++20 -triple x86_64-unknown-linux-gnu -fclangir \
  -I mlir/include -x c++ clang/test/CIR/Transforms/skeleton-manual-path.cpp \
  -emit-cir -o - | head
```

看 module attributes 那一行：`cir.default_tls_model`、`cir.lang` 等，还有 `dlti.dl_spec`（spec 末尾嵌了 `!cir.ptr<!cir.void>` 和 `#cir.ptr_spec`）。另外每个 `cir.func` 上还挂着 `cir.target-features`。看完了再回到代码，能看出两个设计点：

- 函数级的 `cir.*` 不用单独删，因为转换时根本不拷属性——CirCallLowering.cpp 68-70 和 197-199 用 `func::FuncOp::create` 新建函数，只设 `symVisibility`。所以只要管 module 级就够了；
- 删除放在 168 行，在所有 rewrite / erase 之后，因为只有 pass 真正降级完，模块属性才能安全删。

## 第 3 步：看 runOnOperation 主干（CirCallToSkeleton.cpp 67-169 行）

整个 pass 的顺序是：收集信息 → 两个 early-return（72、116 行）→ 转纯函数（123 行）→ 逐个 rewrite 宿主（130-151 行）→ 擦除原 CIR 函数（154-166 行）→ 删模块属性（168 行）。看的时候注意那两个 early-return 都在删属性之前——这意味着「输出能被 mlir-opt 解析」只在模块里没有普通 CIR 函数（非 skeleton 的 helper、main 之类）时才成立。

## 第 4 步（可选）：CirCallLowering.cpp 的三个函数

`convertPureFunctionsToFunc`（30 行）、`rewriteToStandardFunc`（154 行）、`lowerMapCall` / `lowerReduceCall`（207 / 254 行）。只想看一个就挑 `rewriteToStandardFunc`：它怎么把 `float*` 参数变成 `memref<?xf32>`，又怎么按 op 语义凭空定出返回的 tensor 类型——手动路径「宿主签名被重写」的关键就在这。

## 第 5 步：e2e 的 RUN 链

cpp-map-add.mlir 11-21 行是这条链路的完整闭环：clang 编 C++ → cir-opt 降级 → awk 把 module 外壳去掉（13 行）→ cat 拼上 driver → mlir-opt 全链 → mlir-runner。停在 awk 那行想一下它的隐含假设：它认为输出第一行就是 module 头、最后一行就是 `}`，中间没有别的。这个假设现在成立（实测输出第一行是 `module @"/路径" {`），但它经不起变化——cir-opt 的输出格式只要变一点（比如删属性的逻辑没生效，module 头带上多行属性），awk 就会静默拼出坏掉的 MLIR，而不是报一个清楚的错。

## 复核疑点时看哪

- dlti 被整条删掉：CirCallToSkeleton.cpp:55 的 `name.starts_with("dlti.")`。对照第 2 步 clang 输出的 `dlti.dl_spec`——其实大部分条目（`!llvm.ptr`、`i64`、`"dlti.mangling_mode"` 等）mlir-opt 都认得，只有末尾 `!cir.ptr<!cir.void>` 这一条不认得，整条删等于把数据布局也一起丢了；
- awk 去 module 外壳这一步依赖的假设很脆弱：见第 5 步；
- Test 5 没覆盖 dlti 分支：cir-call-to-skeleton.cir 111-130 行的 module attributes 里只有 `cir.*`，没有 `dlti.dl_spec`，所以删 dlti 那半条逻辑只有 e2e（编真实 C++）能拦住。

## 遗留的 TODO

review 时发现留待后续的工作：

1. **支持 host 周围的普通 C++ 代码（核心）**。`cir-call-to-skeleton` 目前只接受「整个 module 都是 skeleton」——runOnOperation 末尾对残留的 `cir.func` 硬报错（本提交新增），所以 main、调用宿主者、任何非 skeleton 函数都编不过。真实程序的 skeleton region 是嵌在正常 C++ 里的，宿主需要被周围代码调用。方向：把宿主改成函数级、保留符号（wrapper + 内部 skeleton op），签名/长度/返回在 host–skeleton 边界上定，而不是 erase 掉整个 `cir.func`。

2. **长度作为一等数据**。host 用裸 `float*`，长度在程序里不存在，pass 只能靠 `outputTensorType` 按 op 语义「发明」输出形状（map → 1D 动态、reduce → rank-0）。要换成 `std::vector` 之类带长度的容器、或 region 显式带长度参数，让 memref 的动态 extent 有真实来源、并能校验多个输入长度一致。成本在 CIR 侧要能识别 std::vector 的 data/size（libc++ interop），或把 helper 约定为 data() + size() 拆传。

3. **去掉 e2e 的剥壳/拼接**。本提交用 `skeleton-peel-module.sh` 把 awk 拼 module 壳改成「校验 + 大声失败」（过渡方案）。彻底解法两条：a) 等 TODO 1、2 落地后，把 @main 也写进 C++，整段 clang → cir → skeleton → run 一条龙、零拼凑；b) 拆分职责——clang 前端正确性交给 FileCheck（已覆盖），lowering + runner 用纯 MLIR 单文件测，运行测试不再吃 C++ 产物（代价是丢掉「clang 真实产物可运行」这条端到端保证）。

4. **dlti 外科化删除**。现在 `dropCirModuleAttrs` 把整条 `dlti.dl_spec` 删了；其实只有末尾 `!cir.ptr<!cir.void> = #cir.ptr_spec<...>` 这一条需要 CIR，其余（i64 位宽、小端、mangling、stack alignment）mlir-opt 都认。只滤掉嵌 CIR 类型的 entry、保留其余布局，等 struct / 对齐敏感的路径出现会需要。

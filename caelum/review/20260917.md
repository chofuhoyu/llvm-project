# 20260917：方向调整与后续计划

这份文档记两件事：一是这次定下的方向调整（论文定位、技术路线、motivation 怎么写）；二是核实过代码之后排出的后续计划——哪些已经做完了不该再当待办，哪些是新的前提，按执行顺序排。

## 〇、背景

这份文档假设读者从零开始，需要的上下文如下。

**项目是什么。** 在 ClangIR / MLIR 技术栈上做一层结构化计算抽象（skeleton dialect）：程序员在 C++ 里用 annotation 标出计算模式（`skeleton.map`、`skeleton.reduce` 这类骨架算子）和无副作用计算（标记为 `skeleton.pure` 的纯函数），以及硬件偏好（`skeleton.preference`，取值 CPU 或 GPU）。编译器识别这些标注，把程序切成可以分派到不同设备上的形态。

**项目原本的三层规划。** 语义表达（语言层的 annotation）、编译管线（skeleton → linalg → 各目标 lowering）、调度（把程序切分并分派到异构算力上）。前两层有代码，第三层一直标着「规划中」。

**这次调整改了什么。** 两件事：

1. **技术路线**：原来是在 ClangIR 上做后验分析、把信息「恢复」成 skeleton dialect；改成在 codegen 期同时产出两种方言（见 1.1）。
2. **论文定位**：目标场合是 TPDS（IEEE Transactions on Parallel and Distributed Systems，A 类期刊，滚动投稿）；主贡献从编译管线移到运行时调度，论文按系统论文来写（见 1.2）。

**本文档用到的两个名词。** 「混合 codegen」指上面第 1 条的做法：同一份 C++ 源码，标了 skeleton 的部分生成 skeleton dialect，其余生成 ClangIR，两者在同一个 MLIR module 里共存。「运行时调度」指第三层：编译期生成候选形态，运行时按实际设备状态选定，不满足就换一个。

## 一、方向调整

### 1.1 起因

做半自动路径（`skeleton.map` 从 annotated 的 `cir.for` 恢复）时发现：ClangIR 相比 C++ AST 已经丢掉了大量信息，一个算子就要几百行模式匹配，而且里面有一半是在猜——反向追 `store → alloca → load` 才能找到 host 的入口参数、输出形状按算子语义凭空发明、长度在程序里根本不存在。算子种类一多，这套恢复规则的组合会迅速失控。

于是技术路线改成：**在 codegen 阶段同时产出两种方言**。程序员标了 skeleton 的部分直接生成 skeleton dialect，其余部分照常生成 ClangIR，两者在同一个 MLIR module 里共存，之后再走 MLIR 自己的 lowering 管线。ClangIR 的地位从「基础」变成「把 C++ 程序完整带进 MLIR 世界的工具」。

### 1.2 论文定位：这是一篇系统论文，不是编译论文

目标场合是 TPDS，A 类期刊，滚动投稿。这个选择决定了整篇论文的写法：**TPDS 的审稿人是并行/分布式系统的人，不关心 dialect 设计得多优雅，只关心跑起来怎么样、比什么快、在什么规模上成立。**

所以主贡献是**运行时调度与设备适应**——项目三层规划里那个一直标着「规划中」、独立于 pipeline 的调度层；编译管线部分（混合 codegen）是让调度成为可能的手段，不是卖点。

核心主张：

> 现有的异构编程模型把目标设备在编译期钉死——源码里写了 offload 到 GPU，运行时 GPU 不在、或被别的进程占满，程序就只能等或崩。我们让程序员只表达计算模式和偏好（软约束），编译期生成候选切分形态，运行时按实际设备状态选定并回退，同一份二进制在设备可用性变化下保持可执行且性能不崩。

这条主张有一个对手**结构上做不到**的点：OpenACC / OpenMP target 的设备绑定是编译期的，不是实现得不好，是模型决定的。

**判定这条主张的实验（下面一律叫「设备争用实验」），同时也是论文的核心图。** 它现在还不存在，本文档后面的台阶 1 就是为了把它做出来。形状是这样：

- **横轴**：GPU 的争用程度——另一个进程占着 GPU 的 0% / 25% / 50% / 75% / 100%（粗糙一点也可以只分「GPU 空闲 / GPU 被占」两种）；
- **纵轴**：同一份负载的完成时间（或者更简单地记「跑得完 / 跑不完」）；
- **三条曲线**：我们的系统（GPU 空闲时上 GPU，被占时回退 CPU，曲线基本平）；OpenACC / OpenMP target 版本（编译期绑死 GPU，被占时时间飙升或直接失败）；纯 CPU 的 OpenMP 版本（一直那么慢，作地板）。

这条曲线画出来，「运行时适应比编译期绑定强」就从主张变成了数据。

需要同时讲清楚的差异化定位：

- 相比重写型方案（CUDA / SYCL / Kokkos）：我们是单源、增量，老代码加标注就能用，不需要重写、不需要两份代码。
- 相比 offload 标注（OpenACC / OpenMP target）：我们保留了单源，但目标选择发生在运行时，设备不可用时能回退。
- 相比显式任务运行时（StarPU 这类）：程序员不需要手写任务图，切分单元由骨架算子和纯函数的结构给出。

### 1.3 为什么能在编译期生成多个候选

审稿人一定会问一个设计问题：**为什么不先生成统一的中间表示，再在上面做分析/转换？**

答案是：提升所需的语义信息——容器类型、元素种类、形状来源、生命周期——在源码层是完整的，一旦降低到任何中间表示，就只能靠模式匹配重建，重建规则会随算子种类增长而迅速复杂化。（这是设计约束的陈述，**不要在 motivation 里写成「我们试过某条路然后失败了」**；也不要提 ClangIR，那个名字对 TPDS 读者没有信息量，提了反而招来一个没必要被问的问题。）

### 1.4 混合 codegen 和调度是同一件事的两面

语义边界（值语义的 tensor/纯函数 ↔ C++ 的可寻址内存语义：别名、生命周期、可变性）看起来是另一个课题，其实是细粒度调度的前提——只有两种方言的数据表示能在同一个程序里安全共存，调度器才有东西可调度。不要把「混合 codegen」（在 codegen 期同时产出 ClangIR 和 skeleton 两种方言）和「运行时调度」（决定哪段算在哪台设备上跑）当成两个平行的大工作，它们是一个工作的两个侧面。

### 1.5 motivation 章节不写什么

- **不写「某条信息在 ClangIR 里没了、我不得不猜」。** 那是工程记录，不是 motivation。理由见 1.3：论文不叙述自己走过的弯路，这跟代码注释里「不描述被否决的方案」是同一条原则。
- motivation 该写的是系统问题：异构执行已是常态，但在 C++ 里用上它仍然要付代价；三条现有路径（重写 / offload 标注 / 显式任务运行时）各自的代价；缺口是「单源 + 增量 + 目标选择在运行时」这三者同时满足的方案不存在。

### 1.6 调度器不是 StarPU

StarPU、OpenMP tasking 那类之所以复杂，是因为要调度**带依赖关系的任务图**——依赖分析、就绪队列、拓扑序。我们的模型里没有这个：纯函数无副作用，骨架算子之间只有 region 嵌套带来的结构层次，没有任意依赖图。要解决的问题是**设备选择与适应**，不是图调度，难度差一个数量级。这件事本身值得写进论文。

### 1.7 调度器的形态：独立 driver

调度器不是 MLIR pass，也不是构建脚本，而是 LLVM 项目里一个独立程序（driver），与 clang driver 同级。这不只是形式要求，它决定了贡献落在哪里：

- **它拥有编译管线，不只是选一个编好的产物。** 输入是 skeleton 层（`skeleton-to-linalg` 之后、`preference-partition` 之前）的 module；驱动器查设备状态、决定这次的 target、用这个 target 跑完剩下的管线、执行、失败就换一个 target 重来。如果它只是「读两个预编译二进制、选一个 exec」，那它就是换了语言的 shell 脚本——**区分的标准是它有没有拥有管线**。
- **preference 从源里的硬标注，降级成驱动器排序时的权重之一。** 这是整个论文主张的实现落点：程序员表达的是偏好，不是绑定。
- **驱动器编排子工具是正当的，不是偷懒。** clang driver 自己也不写目标码，它编排 `-cc1`、汇编器和链接器。所以驱动器调用 `mlir-opt` / `mlir-runner` 就是 LLVM 的 driver 概念本身。以后要自包含（in-process pass pipeline + ExecutionEngine）再说。

位置建议 `mlir/tools/skeleton-driver/`，和 `mlir-opt`、`mlir-runner` 同级——它消费的是 MLIR。将来要驱动 C++ 编译（调 clang 出 CIR、再跑 skeleton 管线）时可以升级成 clang 那一级的工具。

要注意的是：**驱动器的难点不在管线编排，在调度决策**——怎么判定「设备被占」、代价模型怎么算、回退的触发条件是什么。形态要真，功能要少。

## 三、后续计划（按顺序）

### 台阶 0：让台阶 1 跑在真实 C++ 上的前提

下面这些前提不影响纯 MLIR 版本的台阶 1（那个不需要任何编译器改动），但要在真实 C++ 源上跑，必须先补上。

**前提 1：宿主 API 携带长度，而不是裸指针。**

宿主参数现在是裸 `float*`（见 [`SkeletonOps.h:15`](../../mlir/include/mlir/Dialect/Skeleton/SkeletonOps.h#L15) 的注释：`Data arguments are array pointers (e.g. float*)`）。这个签名同时丢掉了两条信息：**有没有长度**，以及**长度是编译期常量还是运行时值**。症状有三个：

1. pass 给所有指针参数一律发 `memref<?xf32>`——动态是硬编码的，不是从类型推断出来的；
2. 输出形状只能按算子语义「发明」（map → 一维动态、reduce → 零维）；
3. 多个输入的长度是否一致无法校验，不一致就静默算错。

修法不用加新机制，关键是**参数类型本身就能表达这件事**，pass 读出来即可：

- **长度编译期已知**——用数组引用 `float (&a)[N]`，`N` 是类型的一部分，pass 直接产出 `memref<Nxf32>`；
- **长度运行时才知道**——用带长度的容器 `std::span<float>`，pass 从「数据指针 + 长度」两个字段取值，产出 `memref<?xf32>`。

用 `std::span` 顺带解决静态/动态的区分：`std::span<float, N>` 和 `std::span<float>` 在类型里就分开了，两种情况共用一个接口，而且它从 `std::vector` 和 C 数组都能隐式构造，用户写法不会变难看。

**不建议用 `std::vector` 直接做参数类型**——那要 pass 去识别 libc++ 的内部布局（三个指针）、调用 `size()`，是版本相关的模式匹配，换个标准库实现就崩。`std::span` 是标准布局的两字段结构，稳得多；实在不行就在 `SkeletonOps.h` 里定义一个自己的 span，用户侧只是多一层包装。

**也不建议只支持静态长度。** 真实负载的尺寸是运行时的，而且台阶 3、4 的数据迁移和粒度切分本质上都要在运行时按长度算——把长度锁死成编译期常量会直接堵死后面的台阶。

**前提 2：长度一旦是运行时值，GPU 桥接就要支持动态形状。**

这条**只在前提 1 选择运行时长度时才存在**：如果 API 用数组引用、长度是编译期常量，产出的是静态 memref，桥接今天就能用，这条前提直接消失。但前提 1 里说了不走那条路，所以这条实际上是要做的。

手动路径产出的 host 签名是动态形状的 `memref<?xf32>`，而 GPU 桥接明确拒绝动态形状（[`SkeletonTargetLower.cpp:127`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L127)）。所以 `mlir/test/Integration/Dialect/Skeleton/GPU/` 下只有一个纯 MLIR 的 matmul 测试，没有 C++ 到 GPU 的 e2e——**现在从 C++ 编出来的东西走不了 GPU 路径**，设备争用实验的 GPU 那一半出不来。

那个 guard 给的理由是「把 host memref 直接透传会让 kernel 读写 host 内存」，所以干脆拒绝。要支持的话，设备侧得按运行时 extent 分配（`gpu.alloc` 本身就收动态尺寸，现在传的是空列表），cast 也要改成带动态 extent 的设备 memref。代码量不大，但下游可能有惊喜——`gpu.memcpy` 带着动态 extent 走完 `gpu-lower-to-nvvm-pipeline` 是否顺畅，要试了才知道。

**前提 3：宿主周围能有普通 C++ 代码。**

这条不影响台阶 1——现有的 C++ e2e 用一份手写 MLIR 驱动 `@main`（`cpp-map-add.driver`）绕开了这个限制。但它影响真实负载：真实程序不会整个 module 都是 skeleton。

现在两条路径都在 module 末尾对残留的 `cir.func` 硬报错——手动路径 [`CirCallToSkeleton.cpp:194`](../../clang/lib/CIR/Dialect/Transforms/CirCallToSkeleton.cpp#L194)，半自动路径 [`CirLoopToSkeleton.cpp:648`](../../clang/lib/CIR/Dialect/Transforms/CirLoopToSkeleton.cpp#L648)。所以 `main`、调用宿主的人、任何非 skeleton 函数都编不过。

方向：宿主改成函数级、保留符号（wrapper + 内部 skeleton op），签名/长度/返回在 host–skeleton 边界上定，而不是把整个 `cir.func` 删掉。

### 台阶 1：驱动器 + 整模块的 target 选择（做出设备争用实验）

**这一步不需要改编译管线，只需要给一个 pass 加选项。**

核实过的现状：`CPU/skeleton-matmul.mlir` 和 `GPU/skeleton-matmul-gpu.mlir` 这两个集成测试**逐字相同**，只差两处——源里 `#skeleton.preference<"CPU">` 对 `<"GPU">`，以及 RUN 行末尾的 lowering 尾巴（CPU 走 `-convert-scf-to-cf ... -convert-func-to-llvm`，GPU 走 `-gpu-map-parallel-loops -convert-parallel-loops-to-gpu -gpu-kernel-outlining -gpu-lower-to-nvvm-pipeline`）。两条都通过（`build/bin/llvm-lit build/tools/mlir/test/Integration/Dialect/Skeleton/` 9/9）。

preference 只在 `skeleton-preference-partition` 一个 pass 里起作用。所以驱动器的做法是：拿同一份 skeleton 层 module，在运行时决定这次跑哪个 target，再用对应的 lowering 尾巴跑完。

要写的是两样：

1. `mlir/tools/skeleton-driver/` 一个新工具（CMake 目标 + 链接 MLIR + 参数处理）；
2. `skeleton-preference-partition` 加一个 `-skeleton-force-target=CPU|GPU` 选项——preference 现在只能从源里来，驱动器没法从外部指定。几十行。

驱动器的第一版只做四件事：

- 查设备状态（能不能建 context、显存够不够、有没有别的进程占着）；
- 按设备状态和 preference 给候选排序；
- 用选中的 target 跑完剩下的管线并执行；
- 走不通就换另一个 target 重来。

**输入先用纯 MLIR。** 现有的静态形状 matmul 测试就够，驱动器不关心输入是 MLIR 还是 C++——这样可以和前提 1、2 解耦，先把不确定性最高的部分验证掉：设备状态怎么查、「被占满」怎么判定、回退怎么触发、候选怎么排序。**这些和输入是不是 C++ 完全无关。** 等曲线出来了，再花那几天把输入换成 C++（前提 1、2）。

判据就是设备争用实验（定义见 1.2）：

> GPU 被占满时，我们的版本退到 CPU 继续跑；OpenACC / OpenMP target 编译出来的版本在同样情况下失败或严重退化。

**形态要真，逻辑可以丑。** 驱动器得是那个驱动器（见 1.7），但里面的判断可以先写死：环境变量覆盖、if-else 排序、固定的代价模型，都行。要真的是「它拥有管线」这件事，不是它的策略有多聪明。

**服务器条件要先摸清楚**：两台机器的 GPU 型号，以及能不能可控地制造「设备不可用」和「设备被占满」两种状态。制造不出来就画不了曲线。

### 台阶 2：preference 软化——每个 op 出两个候选

台阶 1 里驱动器选的是整个模块的 target。这一台阶把选择单元降到每个 op：同一 op 生成 CPU 版和 GPU 版两个函数，驱动器按设备状态给候选排序，preference 是权重之一而不是二选一。做完就有了「软 vs 硬」的消融。

顺带把 20260827.md §6 里的「重复 outline 去重」合到一起考虑：相同 preference、相同 op 形态、相同操作数的 op 现在会各自 outline 成独立函数（[`SkeletonPreferencePartition.cpp:75`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonPreferencePartition.cpp#L75) 的 `idx++`），而调度器很可能整个接管这件事，现在单独做可能白做。

### 台阶 3：候选共存的语义边界与数据迁移

台阶 2 之后，同一份计算的两个版本要共存在同一个 module 里——GPU 的设备内存桥接和 CPU 路径必须同时成立。这是语义边界第一次真正挡路的地方，也是 1.4 说的「混合 codegen 和调度是同一件事的两面」落地的地方。

到这里 [`SkeletonTargetLower.cpp:155`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L155) 的地址空间问题会真正爆掉——现在设备内存用的是 host memref 类型（`auto allocType = entry.hostMemrefType;`），靠 NVPTX generic 恰好覆盖 global 才跑得通。单 GPU 路径下这是运气，一旦 CPU/GPU 共存就必须把地址空间显式化。

同一处的单输出假设（[`:221`](../../mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp#L221)，硬编码 `call.getResult(0)`）也归到这里——多个可写 memref、多结果、被写过的 global 都会静默丢 copy-back。

共存一旦成立，紧接着就是数据在边界上的搬运：一个算子落在 GPU、它的消费者落在 CPU 时，结果要搬回来。这也是前提 1（长度）真正开始被需要的地方——搬运量按长度算，而长度只有运行时才知道。

### 台阶 4：动态粒度调整

前面每一台阶的选择单元都是固定的：台阶 1 是整个模块，台阶 2 起是每个算子。这一步让粒度本身可调——一个算子可以切开分到多个设备上，切多细由运行时的设备数量和负载决定。纯函数 + 骨架算子的结构在这里发挥作用：region 嵌套给出结构层次，没有任意依赖图，所以不需要图调度。

## 五、评测要素（动笔前必须先定）

没有 deadline 的时候，最需要的是一个停止条件。设备争用实验那条曲线画得出来，核心主张就成立。为了让它是条能画的曲线，下面这些要提前定——顺序是先定负载，再反推要实现哪些算子，反过来做会白写代码。

**负载**：4–6 个代表性 kernel，至少含一个 reduction、一个 stencil、一个稠密线性代数。覆盖 PolyBench / Rodinia 里几个有代表性的就够。这决定了要走通哪些骨架算子。

**基线**：

- OpenMP（CPU 多线程）——CPU 侧的地板；
- OpenACC 或 OpenMP target（GPU offload）——**主要对手**，设备争用实验的主角；
- 手写 CUDA——只用来证明「性能在可接受范围内」，不用打赢。MLIR 原型在绝对性能上赢不了手写 CUDA，这是结构性的，别去硬碰。

**指标**：相对基线的性能比、设备不可用时的退化和回退表现、annotation 的编译期开销、随规模的扩展曲线。

**消融**：preference 软 vs 硬、单候选 vs 多候选。这两个直接对应论文的两条主张，必须有。

**定位**：主张是「性能保持度 + 可移植性 + 适应性」，不是绝对性能。这个现在就要定死，它决定了跑哪些实验。

## 六、节奏

- 台阶 0 + 台阶 1：把驱动器和设备争用实验打通。
- 台阶 2 + 台阶 3：每 op 出双候选，再解决候选共存的语义边界与数据迁移。
- 台阶 4 + 评测。
- 成稿投出。

滚动投稿加上导师说不用赶 11 月，时间压力不在「来不及」，而在「永远差一点」。期刊审稿周期长（首轮几个月，加大修，投到中一年到一年半是常态），中间的反复成本比会议高得多，**所以这次定位要一次想透，之后不再换坐标系**。

另外要和导师确认三件事，因为他对转向知情、但可能不知道新定位的重心在调度：主贡献是运行时调度/适应、编译管线只是手段；调度器的**形态**是与 clang driver 同级的独立 driver（§1.7），但**功能**砍到「查设备 → 按 preference 排序候选 → 跑管线 → 回退」这四件事，不做完整的策略框架，也不做分布式；收敛线定在 2027 年 3 月左右。

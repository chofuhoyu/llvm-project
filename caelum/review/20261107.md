## 结论

主干是真的做出来了：C++ 整程序一条命令、`cir-skeleton-split` + `skeleton-lower-host-abi` 的
host↔单元 ABI、destination-passing 的单元形状、`skeleton.managed` 的免拷贝路径、benchmark 的
“先比数值再计时”，以及半自动路径的彻底删除，都能在树上找到代码和用例，E1/E2/E3/E4/E10/E11
站得住。但 GPU 这条线的验收证据比文档声称的弱：`skeleton_rt_sync` 同步的是运行时自建的 context，
而 kernel 由 MLIR 的 CUDA wrapper 在它自己 retain 的 primary context 上启动，在正常驱动上这个等待
并不覆盖 kernel；managed 路径又没有拷贝或 dealloc 作为兜底，所以 E6 的“显式同步”很可能名不副实。
更麻烦的是所有 C++ GPU 用例只比对数值、不检查放置，运行时在 GPU 编译失败时会静默回退 CPU，因此
E5/E7/E8 的“设备上跑出期望值”在这些用例里无法区分“真的在设备上”和“悄悄退回 CPU”。这是本次
审查认为的最大风险：不是功能缺失，而是“绿了但证明不了”。

## 代码质量问题

### 1. ［高］`skeleton_rt_sync` 同步的不是 kernel 所在的 context

`mlir/lib/Dialect/Skeleton/Runtime/SkeletonRuntime.cpp:229-236` 让运行时 `cuCtxCreate` 一个自己的
context；`:244-254` 优先用它，并且只在它“不是当前”时 push、用完 pop；`:337-345` 的
`skeleton_rt_sync` 因此调用的是 `cuCtxSynchronize()` 作用在这个私有 context 上。

而 GPU kernel 是单元模块里生成的 `mgpuLaunchKernel` 启动的，MLIR 的 wrapper 在每次入口都
`cuCtxPushCurrent` 它自己 `cuDevicePrimaryCtxRetain` 出来的 primary context
（`mlir/lib/ExecutionEngine/CudaRuntimeWrappers.cpp:83-100`，启动在 `:171-196`）。`cuCtxSynchronize`
只等待当前 context 的已提交工作：在 primary push 成功（这是正常驱动的行为）的机器上，kernel 在
primary，sync 在私有 context，这个等待不覆盖 kernel。

后果集中在 managed 路径：它没有 copy-back、没有 `gpu.dealloc`，kernel 与宿主读之间唯一的顺序就是
这一次 sync（`SkeletonTargetLower.cpp:221-234` 插入，managed 目标跳过桥接）。如果 sync 是空操作，
宿主会直接读一块正在被 kernel 写的 UVM，属于竞态；小负载下通常“看起来对”，`compute-sanitizer`
的 memcheck 也不负责抓这种顺序错误，所以现有 10/10 与 0 errors 不能排除它。

反过来，如果这台机器的驱动真的像 D8 记录的那样拒绝 push primary，kernel 会落到运行时私有
context 上，sync 反而生效——但这是依赖“驱动拒绝标准 API”的偶然正确，换一台正常机器就没了。
而且 wrapper 的 `~ScopedContext` 在 push 失败后仍然无条件 pop（`CudaRuntimeWrappers.cpp:100`），
正是 D8 描述过的“弹掉别人的压栈”，当前代码并没有消除这个失败模式。

### 2. ［高］C++ GPU 用例无法区分“在设备上”和“静默回退 CPU”

`SkeletonRuntime.cpp:484-519`：偏好 GPU 的单元编译失败时，`provider` 返回 NULL，循环继续到 CPU
候选，CPU 实现编译成功就 `choose=CPU`，只留下 `reason=no-implementation` 的一行 trace，程序照常
输出正确数值。C++ 的 GPU 用例没有一个检查 trace：

- `mlir/test/Integration/Dialect/Skeleton/GPU/cpp-softmax.mlir:4-8` 的注释明确写着“归约上不了设备
  会让这条测试失败，而不是变成悄悄变慢的程序”——这句与运行时行为相反；用例只 FileCheck 数值。
- `GPU/cpp-managed-add.mlir:13-15`、`GPU/cpp-map-add-static.mlir:9-11` 同样只比数值。
- `Benchmark/bench.mlir:17-19` 的“GPU 可用”跑法在无 GPU 的机器上也会落到 CPU，仍打印 `ok`。

于是 E5/E7/E8 里“GPU 上跑出期望值”的断言，实际只能证明“这份程序在某种放置下数值正确”。
对照 `GPU/driver-matmul-gpu.mlir:20-22` 与 `GPU/driver-adaptive.mlir:16-21` 是有
`compile device=GPU`/`choose=GPU` 断言的，说明能力存在，只是 C++ 用例没接上。

### 3. ［中］同步与释放的失败路径全部静默

`skeleton_rt_sync`（`SkeletonRuntime.cpp:337-345`）忽略 `withPrimaryContext` 的返回值和
`ctxSynchronize` 的返回值：拿不到 context 或同步失败时，宿主仍会继续读回。`skeleton_rt_free`
（`:393-411`）同样忽略 `memFree` 的返回值，取不到 context 时 managed 内存直接泄漏。分配失败会
`exit(1)`（`:363-372`），这三处却没有任何诊断，属于“出错就静默降级”的一类。运行时是 v1、
失败即退出的契约本身没问题，但至少应打印原因。

### 4. ［低］`withPrimaryContext` 的名字与注释已经和实现不符，且有一个未使用的局部变量

函数名和文件头注释（`SkeletonRuntime.cpp:204-208`）仍然说“Run `fn` with the primary CUDA
context of the default device current”，但实现从 D8 起优先使用 `privateContext`（`:244-245`）。
另外 `:242` 的 `bool haveCurrent = …` 赋值后没有被使用（后面的判断直接比较 `current != context`），
`-Wunused-variable` 会报。这两处都是 D8 改上下文时漏掉的。

### 5. ［低］`exec=` 字段没有任何测试

`skeleton_rt_resolve` 与 `skeleton_rt_dump_stats` 末尾确实追加了 `exec=`（`SkeletonRuntime.cpp:528-534`、
`:585-596`），D6 说“现有 TRACE 前缀匹配不受影响”，这点是对的（FileCheck 的 `TRACE:` 只匹配行内
子串）。但全仓没有一条 `exec=` 的断言，字段是否接错（例如恒为 0 之外的值）不会被发现。
`driver-adaptive.mlir:16-21` 是最自然的落点，加一个 `exec=0` 即可。

### 6. ［低］几处注释已不再描述代码

- `mlir/lib/Dialect/Skeleton/Transforms/SkeletonTargetLower.cpp:14-22`：文件头只说“每个 GPU 调用
  操作数都分配 UVM 并拷贝”，没有 managed 跳过的说明；pass 的 description（`Passes.td`）更新了，
  文件头没跟上。
- `mlir/test/Integration/Dialect/Skeleton/Benchmark/bench.cpp:13-16`：“The third allocates its
  buffers from the runtime”——第三个负载是 matmul，用的是静态数组；用运行时缓冲的是第四个
  map-add。
- `clang/lib/CIR/Dialect/Transforms/CirStripCIRAttrs.cpp:1-2`：文件头被折成
  `//===- … -*- C++` / `//-*-===//` 两行，`-*- C++ -*-` 标签裂了。

### 7. ［低］`populateCIRToLLVMPasses` 靠 `static_cast` 塞选项

`clang/lib/CIR/Lowering/DirectToLLVM/LowerToLLVM.cpp:5832-5840` 把 `createConvertCIRToLLVMPass()`
返回的 `unique_ptr<Pass>` 强转回具体类型再写 `allowMixedModule`。当前工厂只返回这一种类型所以能跑，
但这绕过了 pass option 的正常构造路径，工厂一变就是未定义行为；给工厂加一个 bool 形参或直接
用 option 的 `PassOptions` 更稳。

### 8. ［低］`skeleton++` 没有 driver 参数直通，挡住 trace 断言

`mlir/tools/skeleton++/skeleton++.sh.in:71` 把任何未知 `-*` 都当 clang 参数，选项里只有
`--link-arg`/`--shared-lib`/`--clang-arg`/`--clang`/`--cir-opt`/`--driver`（`:56-71`）。所以
C++ 用例没法通过 `skeletonxx` 打开 driver 的 `--trace`，也正是问题 2 难以补断言的原因。加一个
`--driver-arg=` 即可。

### 9. ［低］`SkeletonOps.h` 说标量“按值传”，实现是按引用

`mlir/include/mlir/Dialect/Skeleton/SkeletonOps.h:46-47` 写“Scalar arguments … are passed by value
and reach the operator unit as scalars”，但 `:125` 的 `skeleton_map(Fn, const Out &, const Ins &...)`
把标量绑成 `const float&`，切分时看到的是“指向标量的指针”，再在调用前 load
（`CirSkeletonSplit.cpp:200-205`、`CirCallLowering.cpp:151-160`）。`cpp_codegen.md` §10 已经承认
了这个差异，头文件与 `cpp-codegen-operators-decisions.md:49` 没改。

## 决策问题

1. **D3（同步放在单元调用之后、由运行时提供）**：位置与“运行时知道设备、lowering 知道调用点”的
   分工论证成立，代码也照做了。但这条决策漏掉了最关键的一步——同步哪个 context。D3 的理由
   （“同步语义属于运行时，它知道设备怎么来”）在运行时自己 `cuCtxCreate` 之后不再自动成立；
   见代码问题 1。决策需要补一句“同步的是 kernel 所在的那个 context”，并用一个会因乱序而失败的
   用例钉住它。

2. **D8（CUDA context 自己建、自己管）**：理由只论证了 *managed 内存的设备可见性*（“managed
   memory 属于设备而不属于 context”），这对分配是对的，对 `cuCtxSynchronize` 不成立——同步是
   context 范围的。这条决策把 `skeleton_rt_sync` 一并改成走私有 context，却没有记录这个副作用；
   `runtime.md` §14 那一行同样只写了 context 的所有权。记录的诚实性在这里是不完整的：它只
   说了“为了消掉 18 条 push 报错”，没说“代价是 sync 的目标从 primary 换成了私有 context”。

3. **D9（探测不再读空闲显存）**：记录本身是诚实的——写清了背景、选择、代价（“生产路径上不再
   因为显存放不下而回退 CPU，只有显式设置强制值时才会”）。但其余文档没有同步：`runtime.md:173-174`
   仍说 `bytes` 与空闲显存比较、放不下回退；`:234` 的“策略（v1）”仍以“放得下”为条件；
   `SkeletonRuntime.h:53-58` 仍说 `bytes` 用来拒绝放不下的放置。结果是“显存回退”在代码里只剩
   `driver-memory-fallback` 这个强制值用例，文档却像它还是生产行为。

4. **D2（归约 destination 用可写视图，不加新 lowering）**：论证与代码一致，`createToTensor` 的
   `writable` 参数与 `MaterializeInDestinationOp(..., writable=true)` 都落在
   `CirSkeletonSplit.cpp:250-345`，归约在设备上的可行性也有上游 `[parallel, reduction]` 的
   lowering 支撑。唯一没记的是这个改动对 **map** 的副作用：输入视图和可写目的地都带 `restrict`，
   `skeleton_map(f, a, a)` 这种输入输出同缓冲的调用没有任何诊断，属于静默 UB。D2 只讨论了 reduce
   “原地归约不安全”，map 的原地写法本来是安全的，却因为 `restrict` 变成了不安全且不报错。

5. **D4（managed 跳过桥接）**：站得住。全有或全无的检查在 `CirCallLowering.cpp:186-206`，
   混用会编译期报错；“静态数组继续走桥接”也没有改坏。D4 里“一条已通过的路都没动”这句偏乐观——
   桥接路径在这个分支里其实是动过的（可写目的地、每个调用后插同步、去掉异步拷贝），但不是这条
   决策的问题。

6. **D5（`buffer<T>` 一维、运行时长度）**：站得住，代码就是 `{data, size}` + `memref<?xT>`，
   代价（softmax 这类二维算子继续走桥接）也写清了。

7. **D1（过滤器按“谁驱动切分”选）**：站得住，`remote-impl.sh` 与 AGENTS 都改了，理由
   （“按名字选会再漏”）也成立。

8. **D6（executor 只加只读字段）**：方向合理，但 `skeleton_rt_executor_count` 除了注册进 JIT 符号表
   之外没有任何调用者，`exec=` 也没有测试；作为“给以后留锚点”的最小实现可以接受，只是别忘了
   在日志里真正固定它。
